description: Work on or review the protected path that creates an organization with its HQ office, against the current plan and its owning documents.
---

The protected creation path is how an organization and its HQ office come into being. Its requirements are increment A4 of docs/implementation-plan.md ("Create the organization"), and B1b, which moves it onto the office store (docs/design/office-store.md, ADR-0021). Read before changing it: docs/design/create-organization.md, docs/design/organization-data/01-organization-structure.md, the creation parts of docs/design/organization-data/16-recovery-and-office-continuity.md (what recovery means, ownership, storage and rebuilding, and the first directory generation), ADR-0007, ADR-0011 and ADR-0016. The task records under .agent-kit/tasks/ that the skill catalog attaches to this skill are closed records of earlier work; they are not requirements.

What the code has today: the host's `organization.create`, served on the admitted web connection only (crates/org-host/src/provisioning.rs), reserves writer custody for the new office (crates/org-host/src/writer.rs) and carries the selected create payload from crates/org-proto/src/selected_bootstrap.rs to the office worker (apps/agentic-org-office/src/hq_creation.rs). The worker calls `Office::provision_hq` (crates/org-office/src/office/creation.rs): it freezes the creation intent (`hq-creation.v1.json`, bound to the custody reservation), then `CreateOrganizationOp` (crates/org-office/src/store/open/operations.rs) writes the organization, its escrow package and the wrapped CA key record in one journal entry; `office.json` is published only after that entry is materialized. `office_local` (crates/org-office/src/office_local/) owns the key record and the clean-stop marker; crates/org-office/src/hq_creation.rs holds the launch binding. No office database holds the key, wrapped or not.

Rules that hold for any change here:

- The signed-in administrator creates the organization; whoever creates it is its owner. Creation makes one top-level team named after the organization, the creator as a person in it and its lead, and the built-in HR lead as an employee in that team. Organization and office IDs are UUIDv7.
- The CA private key is created in the office worker and is never sent to the host, the web process, a log or any file in the clear. It is stored only wrapped by the host-held office secrets key (ADR-0016), in the HQ's local record `durable/local/offices/<office-id>/security/ca-key.v1.json`, whose one exact form is in data contract document 16 ("The HQ's CA records"). That record and the public escrow package `durable/state/security/ca-escrow.v1.bin` are written by the creation's journal entry, so the protected journal holds the wrapped key until that entry's segment is released; the outbox, Git publication and every export ship only `state/` changes, never `local/` or another protected tree. A retry of the same creation carries the same frozen material and returns the same CA and the same public package; regenerated material is refused as a reused operation; a conflicting public copy is refused and kept.
- Creation is recoverable phase by phase: a crash or a lost reply at any point leaves state from which the same request completes, never a second organization or a fresh owner over an existing HQ. The office is not ready, and binds no socket, until owner authority and the organization's first records are installed.
- The recovery code is released once, on the HQ machine (ADR-0011).
- Bootstrap authority is not a person's session; it grants nothing to a browser or command-line request.
- Nothing has shipped: no migration, legacy compatibility, dual store or second writer. Creation is the first accepted entry of the organization's journal and its first directory generation (B1b); an organization made by the old databases is refused, not migrated. Operation IDs on disk are UUIDv7: the wire's ULID command ID is mapped by `organization::operation_id::from_wire_ulid`.

Prove the path early with an executable test that creates, faults and reopens in a temporary root, through the real worker and store. Test wrong scope or account, missing control, a closed connection, a revoked owner and retry after each phase at the side that enforces it. A test driver is a fixture, not proof of the host's production custody.
