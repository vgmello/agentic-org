## Context

- Under [ADR-0004](decision-4%20-%20ADR-0004-Agent-sessions-run-headless-people-interact-through-chat.md), agent sessions run strictly headless over structured protocols, and there is no terminal in the browser.
- Operators deploying Agentic Org on headless hosts or managing remote satellite offices still need a simple, browser-based way to connect Claude and Codex subscriptions to a pool connection (`provider_connections` / `office_connection_bindings`) without SSHing into every machine.
- [ADR-0015](decision-15%20-%20ADR-0015-Agent-isolation-is-a-selectable-mode-with-a-dedicated-OS-user-provisioned-at-setup.md) decision 11 left two open questions for spike C1:
  1. How each vendor CLI stores and locates a relocated sign-in on macOS vs. Linux.
  2. What happens when multiple agents or multiple offices share one subscription connection whose OAuth refresh token rotates on use.
- The [C1 sign-in spike](../docs/research/doc-25%20-%20Research-C1-Sign-In-Private-Home-and-Sub-Agent-Isolation-Spike.md) (run on macOS `27.2.1` arm64; Linux remains unverified until a Linux run) and [`pocs/console-attach`](../../pocs/console-attach/README.md) showed:
  - Both `claude setup-token` / `claude auth login --claudeai` and `codex login --device-auth` can be driven headlessly in a wide PTY without launching a server browser, yielding a standard OAuth URL (plus paste-back code for Claude, or a one-time device code for Codex).
  - `claude setup-token` produces a portable 1-year `CLAUDE_CODE_OAUTH_TOKEN` (`scope=user:inference`) that avoids macOS Keychain and `HOME` conflicts (Linux runtime behavior remains to be verified on Linux).
  - Codex OAuth refresh tokens rotate on use, so copying one `auth.json` across offices risks `refresh_token_already_used` revocations. A synthetic-token protocol probe against Codex `0.169.0` confirmed `codex app-server` accepts `account/login/start` (`type: "chatgptAuthTokens"`) with **zero `auth.json` written to disk** and emits `account/chatgptAuthTokens/refresh` on an unauthorized token; a live model turn with real tokens and a vendor-supported refresh path remain to be verified before enabling centralized refresh.
- Persistent sessions with background tasks and sub-agents remaining active across turns are owned by [ADR-0025](decision-25%20-%20ADR-0025-An-agent-can-start-sub-agents-inside-its-turn.md) decision 6 (not duplicated here).

## Decision

### 1. Browser-driven one-time enrollment (narrow exception to ADR-0004 decision 3)

1. **Bounded enrollment PTY helper — never an agent terminal.** Under the explicit narrow exception amended into [ADR-0004](decision-4%20-%20ADR-0004-Agent-sessions-run-headless-people-interact-through-chat.md) decision 3, the office worker (`agentic-org-office`) may spawn a short-lived, bounded Unix PTY strictly to execute a vendor's one-time sign-in CLI (`claude setup-token`, `claude auth login --claudeai`, or `codex login --device-auth`) during connection enrollment. It is never exposed as a terminal to the browser, carries no terminal frames or arbitrary keystrokes, and exits or is killed on timeout/cancel. All agent sessions remain strictly headless per ADR-0004.
2. **Structured enrollment API through `agentic-org-web`.** An authorized operator (owner) clicks sign-in in `apps/agentic-org-ui`, calling authenticated `agentic-org-web` endpoints backed by the office worker's enrollment service:
   - **Session binding, concurrency and timeout:** Every `login_id` is bound to the authenticated owner session that created it. At most **one** active enrollment helper may run per `(office_id, connection_id)` at a time, with a fixed timeout (15 minutes) that kills and reaps the helper PTY and wipes its temporary directory.
   - **Claude (`paste_code` flow):** starts `claude setup-token` (preferred) or `claude auth login --claudeai` with `BROWSER=/usr/bin/true`, `NO_BROWSER=1`, and `SSH_TTY=/dev/pts/0` in a wide (`512x24`) PTY; returns only `{ login_id, flow: "paste_code", url, state }`. The owner authorizes in a browser tab and submits the returned code to the API. The service enforces a **strict charset and length check** on the submitted code (printable ASCII token characters only, no control characters or newlines, bounded length) before writing `<code\r>` to the PTY.
   - **Codex (`device_code` flow):** starts `codex login --device-auth` in a PTY; returns `{ login_id, flow: "device_code", url, user_code, state }`. The owner completes device authorization in their browser while the UI polls status until authenticated.
3. **Ephemeral staging and wrapped custody (ADR-0016 decision 3).**
   - **No persistent plaintext on the enrolling host:** Vendor CLIs may write a plaintext credential file during interactive sign-in. Every enrollment helper therefore runs inside a fresh, per-login `0700` temporary config directory (`CLAUDE_CONFIG_DIR` / `CODEX_HOME` and isolated `HOME` where supported) owned by the service user. Immediately after extracting the credential (or on failure/timeout/cancel), the worker **wipes and deletes** that temporary directory so no plaintext credential file persists on disk. (Where `claude auth login --claudeai` would otherwise touch macOS Keychain, `claude setup-token` is used instead so no Keychain entry is created.)
   - **Custodian and separate wrapping key (`TASK-11`):** The **office worker (`agentic-org-office`)** is the custodian of wrapped provider credentials. Extracted credentials are immediately sealed with `org_pki::wrap::wrap_provider_credential` under a **distinct wrapping key** derived via `org_pki::wrap::derive_wrapping_key(office_secrets_key, KeyClass::ProviderCredential)` (separate from `KeyClass::OfficePrivateKey` used for Org CA / TLS private keys, [ADR-0016](decision-16%20-%20ADR-0016-No-application-level-encryption-of-organization-data.md) decision 3) and the dedicated authenticated-data domain `agentic-org/provider-credential/v1` binding `(version, "provider-credential", organization_id, office_id, connection_id)`, stored under `durable/local/offices/<office-id>/auth/<connection-id>/`.
   - Raw tokens, refresh tokens, and submitted codes are **never** returned in debug previews or HTTP error replies, written to logs, stored in Git or SQLite in plaintext, or passed in child `argv` / `SessionSpec`.

### 2. Per-office default custody and optional HQ-to-satellite distribution

4. **Transport and peer identity.** Whenever credentials or short-lived access tokens are delivered from HQ to a satellite, they never travel over plain HTTP or through browser-facing listeners. Delivery uses the existing **Organization-CA mTLS single outbound full-duplex channel** ([offices-hq-and-satellites.md](../docs/design/doc-67%20-%20Design-Offices-HQ-and-Satellites.md#the-invitation-and-connection), [standalone-server.md](../docs/design/doc-70%20-%20Design-Standalone-Agentic-Org-Server.md#6-authentication-keys-and-platform-gates)):
   - Each satellite worker generates and holds its own TLS identity key locally, wrapped under its own office secrets key (ADR-0016).
   - HQ authenticates each satellite by its Organization-CA-signed certificate bound to `office_id` and can revoke an individual office without rotating other offices.
   - If a relay is ever introduced in a future release, payloads are additionally AEAD envelope-encrypted to the target satellite's public key.
5. **Claude (`CLAUDE_CODE_OAUTH_TOKEN`) per-office lifecycle and environment hygiene.**
   - **One token per office binding:** Rather than sharing one 1-year `setup-token` across all satellites, each office binding receives its own minted `CLAUDE_CODE_OAUTH_TOKEN` (minted locally or delivered once over the Organization-CA mTLS channel and wrapped locally by the satellite worker under `KeyClass::ProviderCredential` + `agentic-org/provider-credential/v1`). Revoking or offboarding one office revokes only that office's binding and token without invalidating other offices; each satellite continues running Claude offline when HQ is unreachable ("Works alone").
   - **Expiry, revocation and re-enrollment:** Each binding records token creation and expiry metadata alongside `office_connection_state`. Near expiry, on vendor rejection, or on operator revocation, `office_connection_state` transitions to `auth_expired`, blocking new starts on that route until the owner re-enrolls the binding through the enrollment flow or deletes the revoked binding.
   - **Environment exposure, FD handoff, and redaction (empirically verified 2026-11-21 on Claude Code 2.1.311):** Binary inspection of installed Claude Code `2.1.311` confirmed two complementary protections: (a) `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` activates the internal `U7r`/`lts` scrub list covering `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`, and `CLAUDE_CODE_SESSIONS_OAUTH_TOKEN` for child tool subprocesses; and (b) **`CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`** (`pZr`) reads the OAuth token once from an inherited pipe FD into memory and deletes the env var immediately so `CLAUDE_CODE_OAUTH_TOKEN` never enters `environ` at all. C2/C3 launches MUST prefer one-shot FD delivery via `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` (with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` pinned in `crates/org-agent-runtime-claude/src/plan.rs` as defense-in-depth); if a target runtime build lacks both verified FD delivery and verified env scrubbing, authentication MUST move to a local out-of-process auth proxy before enabling live runs. In addition, the office redacts all provider tokens from event logs, stderr logs, and REQ-05 session-view transcript rendering (`ENROLL-3`). Headless Linux behavior remains marked unverified until exercised on Linux.
6. **Codex: HQ-centralized refresh (`chatgptAuthTokens`) by default for multi-office pools; per-office device login for extended offline use.**
   - **Default multi-office mode (HQ-centralized refresh — owner-approved exception to "Works alone", [architecture-non-negotiables.md](../docs/doc-7%20-%20Architecture-Non-Negotiables-and-Who-Decides-What.md)):** Because Codex OAuth refresh tokens are single-use rotating tokens, HQ is the **default** sole custodian of one Codex `refresh_token` per shared Codex subscription, guarded by a single refresh lock at HQ. Satellites never receive the `refresh_token` and write no `auth.json`. Each satellite passes a short-lived (~1-hour) `access_token` (+ `idToken` / `chatgptAccountId`) to `codex app-server` via `account/login/start` (`type: "chatgptAuthTokens"`). On `account/chatgptAuthTokens/refresh`, the satellite requests a fresh `access_token` from HQ over the Organization-CA mTLS channel and replies to `app-server` without dropping the live session.
   - **Recorded exception & verification gate (empirically audited 2026-11-21 on Codex `0.169.0`):** Generating the protocol schema via `codex app-server generate-json-schema` confirmed that `account/login/start` (`type: "chatgptAuthTokens"`) delivers short-lived tokens over the app-server stdio JSON-RPC channel (never via child process environment variables), `account/chatgptAuthTokens/refresh` is defined as a server request gated on `experimentalApi`, and child tool subprocess environment inheritance is bounded via `shell_environment_policy` (configured with minimal `inherit` / explicit secret exclusion in the Codex runtime plan). Under centralized refresh, a satellite disconnected from HQ can keep running Codex until its current ~1-hour `access_token` expires; this trade-off is explicitly recorded in [architecture-non-negotiables.md](../docs/doc-7%20-%20Architecture-Non-Negotiables-and-Who-Decides-What.md) ("Works alone", owner decision 2026-11-19). Before shipping HQ-centralized refresh in production, implementation must verify: (a) a live end-to-end model turn using real tokens in `chatgptAuthTokens` mode, and (b) a vendor-supported, terms-of-service-compliant refresh mechanism at HQ (without relying on an undocumented OAuth client/endpoint); if either fails or `experimentalApi` breaks on a target Codex build, C2/C3 MUST fall back to per-office device login or a local out-of-process auth proxy.
   - **Optional offline-independent mode:** An office that must run Codex disconnected from HQ for extended periods uses its own independent per-office `codex login --device-auth` binding instead, stored wrapped locally under `durable/local/offices/<office-id>/auth/<connection-id>/`.
   - **Never copy rotating `auth.json`:** Two offices or two concurrent processes must never share or independently refresh copies of the same Codex `refresh_token`.

### 3. Friendly Advanced Settings presets (stored on `agent_execution_configs`, mapped onto `org-agent-runtime`)

7. **Secure by default, explicit mapping, no bypass mode in product code.** An agent's execution configuration (`agent_execution_configs.permission_preset` in [document 11](../docs/organization-data/doc-88%20-%20Organization-Data-11-—-Model-Profiles-and-Agent-Execution.md) and `execution.md`, never on a provider connection) stores one of four presets, defaulting to `safe_ask` with workspace OS sandbox enabled. Each preset maps strictly onto `org-agent-runtime::PermissionMode` plus named `PermissionPolicy` allow rules—always subject to `SessionSpec::effective_permission_mode`, the fixed denies, and mandatory escalation denials (`Escalation::SandboxBypass` always denied; `PermissionChange` and `Unknown` always routed to a person):
   - `safe_ask` *(default)* → `PermissionMode::Ask`, workspace OS sandbox enabled, no implicit allow rules; tool and command approvals route through the owner/policy bridge.
   - `read_only` → `PermissionMode::Plan`, workspace OS sandbox enabled; planning and read-only inspection only, no mutating edits or shell writes.
   - `workspace_edits` → `PermissionMode::AcceptEdits` (narrowed to `Ask` by `effective_permission_mode` whenever a deny-like restriction is dropped; headless Claude still checks file writes at real path through the office per [agent-sessions.md](../docs/design/doc-29%20-%20Design-Agent-Sessions-and-Runtime-Isolation.md)), workspace OS sandbox enabled; workspace file edits allowed, shell commands routed for approval.
   - `autonomous_sandboxed` → `PermissionMode::AcceptEdits` plus a named, bounded `PermissionPolicy` allowlist of workspace-scoped sandboxed commands (never touching managed state or fixed denies, and still subject to `effective_permission_mode` and escalation rules), workspace OS sandbox enabled.
   - **No `unrestricted` / bypass preset in product code.** The `org-agent-runtime` invariant prohibiting skip-permissions / bypass modes (`crates/org-agent-runtime/src/lib.rs`) remains unchanged.

## Acceptance criteria

| ID | Passing evidence |
| --- | --- |
| ENROLL-1 | An owner completes Claude subscription enrollment (`claude setup-token` (preferred) or `claude auth login --claudeai`) from the browser without a terminal; `login_id` is bound to the owner's session, only one enrollment runs per connection, invalid paste-back codes are rejected, the per-login `0700` temp config dir is wiped after extraction, and the token is stored only wrapped via `org_pki::wrap` (`agentic-org/provider-credential/v1`) under `auth/<connection-id>/`. |
| ENROLL-2 | An owner completes Codex subscription enrollment (`codex login --device-auth`) from the browser using the displayed URL and one-time code; cancelling or hitting the fixed timeout kills and reaps the helper PTY and wipes its temp directory with no orphan process or leftover plaintext file. |
| ENROLL-3 | No raw OAuth token, refresh token, or pasted authorization code appears in HTTP error replies, debug previews, event logs, stderr logs, REQ-05 session-view transcripts, Git, SQLite tables, or child `argv`. |
| ENROLL-4 | Each office binding holds its own wrapped `CLAUDE_CODE_OAUTH_TOKEN` (delivered locally or over Organization-CA mTLS), continues working when HQ is disconnected, transitions to `auth_expired` on expiry or revocation, and supports clean re-enrollment without disturbing other offices. |
| ENROLL-5 | In the default multi-office Codex mode (once live model turn + vendor-supported HQ refresh are verified), satellites write no `auth.json`, run Codex using HQ-delivered `chatgptAuthTokens`, handle `account/chatgptAuthTokens/refresh` via HQ's single-lock refresher, and reject concurrent refresh races cleanly; an office configured for extended offline use binds independently via `codex login --device-auth`. |
| ENROLL-6 | Revoking a satellite's Organization-CA certificate immediately causes HQ to refuse subsequent credential fetch/refresh requests from that office, and revoking that office's Claude binding invalidates only that office's token. |
| ENROLL-7 | Advanced Settings on an agent's execution configuration (`agent_execution_configs.permission_preset`) exposes only the four presets mapped onto `PermissionMode` + `PermissionPolicy`, defaults to `safe_ask` with OS sandbox enabled, and rejects any bypass/unrestricted request. |

## Consequences

- Headless hosts and remote offices can be authenticated from the web UI with zero SSH and without exposing a browser terminal for agent sessions (ADR-0004).
- Claude (per-office wrapped 1-year `setup-token`) honors "Works alone" when HQ is unreachable; multi-office Codex defaults to HQ-centralized refresh under the explicit exception recorded in [architecture-non-negotiables.md](../docs/doc-7%20-%20Architecture-Non-Negotiables-and-Who-Decides-What.md) (~1-hour offline access-token window, with optional per-office `codex login --device-auth` for extended offline operation).
- Per-office Claude tokens allow revoking a single compromised or offboarded office without disrupting other offices.
- Wrapping provider credentials under the separate `agentic-org/provider-credential/v1` AEAD domain preserves key-purpose isolation with ADR-0016's `agentic-org/office-private-key/v1`.
- HQ-centralized Codex refresh (`chatgptAuthTokens`) requires `experimentalApi: true` on Codex `0.169.0` and remains gated on proving a live model turn and a vendor-supported refresh path before shipping.
