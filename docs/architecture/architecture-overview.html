Agentic Org · Architecture

Architecture overview

Agentic Org is a self-hosted server that runs an organization of AI agents and people: teams, projects, tasks, chat and spend, with agents launched and supervised on machines you control. This page is the map. It names the parts, what each one owns, where truth lives, and how far the code is from the selected design.

01The product in one minute

An owner installs one server, creates an organization, and staffs it with employees. Some employees are people and some are AI agents. The server keeps the organization's structure and work as files in a Git repository, runs each agent as a supervised child process, routes messages between employees, and accounts for what the agents spend.

  • Organization. A tree of teams. Every employee, agent or person, has exactly one home team.
  • Offices. The machines where agents run. One office is HQ and holds organization authority. Satellites are additional machines running the same worker.
  • Work. Projects contain features and typed tasks (task, bug, request). Releases and deployments record what shipped.
  • Two front doors. People use a browser. Agents use the agent-os command-line tool.
  • Files first. Definitions and open work are files in the organization's Git repository. Databases index them.

The architecture was a desktop app and is now a standalone server with browser access (ADR-0005). The desktop shell is removed. Nothing was deployed under the old shape, so there is no user data to migrate.

Today the black path is: the host starts an office worker and hands it its database key, the worker serves organization, work and messaging commands on a Unix socket, and agent-os talks to it. Install and update: a person installs one thing

A person installs only agentic-org. Everything else arrives through it.

  • Install. A small bootstrap downloads and verifies agentic-org and runs setup. Setup fetches the rest as one complete signed release (the office worker, the web server, agent-os and the UI), verifies it, and pins it. An offline install takes a local bundle and makes no network request.
  • Update, including itself. A release always contains all four executables and the UI, so updating is one operation. The running host looks for a new release in the background, stages and verifies it, drains the instance, switches the pin, and the service restarts on the new agentic-org. agentic-org upgrade does the same on demand.
  • Safety rules. The previous release is kept. An executable is never rolled back alone after an incompatible data change. An update source that cannot be reached never blocks startup.

Accounts, people and agents: who holds what

  • Accounts and sessions belong to the host. The office and the web process never hold a password. Exactly one account is the server's administrator; it is the first account, created from a one-time link that setup prints.
  • Setup creates no organization and no office. The headquarters office comes into being with its organization, when the administrator creates it.
  • Every account is tied to a person. So every change is recorded under a person or an agent. There is no nameless owner: the owner is a person, and being the owner is a permission of their account at the host.
  • Agents exist only as employees hired through HR, which is built into the product, and they are started only by the office.
  • No access roles. A person is whatever place the owner gives them in the hierarchy. Anyone with an account can read the organization, work on tasks and talk to any person or agent. A short list of rights is reserved: the administrator creates organizations; the owner changes the structure; either invites people; a hire is approved by the owner or someone in the lead chain of the team the agent joins.
  • The host's database can be lost without losing the organization. The files are the source, so an existing organization can be opened again from its repository on a server that has no record of it.

The screens and steps for installing, registering and inviting people are product behaviour, not architecture. They are in docs/specs/server-installation-and-access-ux.md.

Designed The standalone design gives serve "the host, key custody, child supervision and update management". The release verifier library exists; no download, staging or activation runs yet (checklist rows FC-022 and FC-154).

Web sessions: why they are in memory today, and how to stop signing people out

Today two things live only in memory: the web process's link between a browser's cookie and its session, and the host's own list of sessions (a map in memory, not a database table). The design ties a session's life to the connection between the web process and the host, so when either restarts, every browser is signed out.

It was designed that way for three reasons. None of them is a hard requirement.

  • The web process faces the network, so it is sandboxed and given no key and no database. It has nowhere to keep anything.
  • Ending a session is instant and certain: remove it from the list. Sign-out, a password change and removing someone's access all take effect at once.
  • A restarted web process cannot pick up sessions it did not create.

You are right that this is not needed. There are two ways to keep people signed in across restarts. In both, the web process still holds no secret, and the state belongs to the host, because accounts are per instance and the host owns them.

ApproachHow it worksEnding a session earlyWhat it adds
Signed tokens (your proposal)At setup the host generates a key pair and keeps the private key in its custody. At sign-in it signs a token. The web process gets only the public key and checks each request's token itself. Nothing is stored per session.Not instant by default: a signed token stays valid until it expires. It needs a short life (minutes) with renewal through the host, plus a per-account "sessions valid from" marker in the host database so a password change or "sign out everywhere" takes effect at once.Key generation and rotation, a token format, clock handling, the marker.
Stored sessions at the hostThe host writes each session as a row in its database. The browser keeps today's random cookie. After a restart the web process asks the host once per cookie and carries on.Instant, exactly as today.One small table and one lookup after a restart.

Decided 2026-11-17 (ADR-0013). v1 uses stored sessions with the cookie. The web process keeps them in memory and re-checks a cookie with the host once after a restart; sign-out deletes the session from the store and from memory. Signed tokens are a v2 option.

It does not go to the database on every request. The web process asks the host only the first time it sees a cookie, for example after a restart. After that it answers from memory. The store holds a fingerprint of the cookie, never the cookie itself, so a copy of the database cannot be used to act as someone.

Why the host, and not the web process, would own a key. The web process does not check passwords. It passes the sign-in to the host, which owns the accounts, checks the password and applies lockout. So the host is the one that knows who you are. The web process is also the part exposed to the network, which is why it is given no secrets and no storage: if it held a signing key, breaking into it would let someone create a valid session for any account, including the owner. And with no storage of its own it could only keep a key it made at start-up, which would sign everyone out on restart again. For v1 the question does not arise, because nothing is signed.

Testing the API. A test signs in exactly as a browser does: it creates a throwaway instance with a test account, calls the sign-in endpoint, keeps the cookie and the second value it returns, and sends both on every call. That is the supported way to script the API in v1. There is no test-only shortcut in a production build. Tokens for scripts and other non-browser clients come with the v2 token work.

agent-os speed: where 15 ms comes from, and how to get to 1 to 2 ms

The 15 ms figure is the target for sending, which is a write. It is not the cost of agent-os as a whole; reading an inbox is targeted at under 2 ms. ADR-0003 breaks a send down like this (design estimates for an Apple Silicon Mac):

StepEstimateWhy
Start the agent-os processabout 2 msThe operating system loading and starting a program.
Connect to the office and identifyabout 0.5 msOne local socket exchange.
Wait for the disk6 to 10 msThe rule "answer only after the write would survive a power cut". On a Mac that needs a full flush to the drive, which is slow.

What "waiting for the disk" means. There already is a local office database, on the same machine. Saving to it has two stages. First the database accepts the write: it is recorded and visible, but still sitting in the operating system's memory. That takes microseconds. Second, the operating system is told to push it onto the physical drive, so it would survive the power being cut. That takes milliseconds, and on a Mac the reliable version of it is especially slow. Today the office waits for the second stage before it answers.

I measured both stages on the Linux machine this was analysed on. A database commit that waits for the drive took 0.29 ms; one that does not wait took 0.013 ms, about twenty times faster. On a Mac the gap is larger, because the wait is the 6 to 10 ms above.

Decided in direction 2026-11-17 (ADR-0014). "The database accepted it" is enough for chosen operations. The office answers as soon as the write is committed, and pushes it to the drive within a short bounded time afterwards. The target is a median of 1 ms and 2 ms at worst for nearly all calls. What you accept: a message acknowledged in the instant before a power cut can be lost. A crash of the office alone loses nothing.

So the software is not slow. It is waiting for the disk because of a durability rule, and it pays for a fresh process every call. The writer already batches, so sixteen agents sending at once share one flush, but a single send still waits for one.

I measured the process start. On the Linux machine this was analysed on, starting a program that does nothing takes about 1.1 ms, and agent-os --version about 1.5 ms (median of 1,000 runs; 95% under 2.2 ms). A Mac is typically slower at this. A budget of 1 to 2 ms is therefore used up by starting the process, before any work is done.

Getting to 1 to 2 ms needs two changes, and both are available:

  1. Answer once the database has accepted the write. This is the decision above, and you set its scope: messaging (send, reply, mark read or done, status) and non-critical task activity (comments, checklist ticks, watching) use the fast answer. One exception: a comment that asks the owner a question, or answers one, stays strict, because it starts or ends a wait. Creating a task, changing its status, assigning it, organization changes, numbering and budget actions keep waiting for the drive, because losing one of those silently is worse.
  2. Stop starting a process per call. Keep one agent-os process open for each agent session and send requests down it. Each call is then one exchange on an open local socket, which takes a fraction of a millisecond. The session design already gives every agent an office-provided tool configuration that a long-running helper fits into.

Kept independent of the database. You asked that this survive a later move to PostgreSQL. So each operation states once, in the domain code, whether it needs the fast or the strict answer. The storage layer decides how to deliver that for the database in use. Domain code never mentions a database setting, so a second database only has to honour the same two promises.

With both, a send lands well inside 1 ms. With only the first, a Mac is bounded by process start at roughly 2 to 3 ms. For scale: one model call takes hundreds of milliseconds to seconds, so this matters for load with many agents more than for what one agent feels.

Two smaller facts. The binary built here is 1.56 MB on Linux, above the 1 MB target; the target was written for a Mac build and I could not check that. The speed decision is ADR-0014.

Send and ask (decided 2026-11-17). A plain send answers in single-digit milliseconds in every topology, also when the recipient is in another office. The sender's office saves the message locally and answers. Relaying it through HQ to the other office happens afterwards and is retried until it arrives or the message expires; a failure becomes a delivery notice, never a slower send. An ask is the one operation that holds its caller. It always has a deadline, the sender may say how long a reply is expected to take, and it returns a timeout when the deadline passes.

Asking and waiting (decided 2026-11-17, ADR-0020). When an agent asks a person or another agent, it waits for a bounded time: a setting, 10 minutes by default, the same for both. The agent says whether the answer is required, meaning it cannot continue without it.

  • Answered in time: the agent gets the answer and carries on.
  • Not answered, not required: the ask returns a timeout. The agent decides: carry on, ask someone else, or declare that it does need this answer.
  • Not answered, required: the system tells the agent to finish or stop its background work, then shuts the agent down. Its context is on disk. The question stays open.
  • When the answer arrives: the system starts the agent again in the same session and hands it the answer. For the person, the agent was simply idle until they replied.

A stopped agent holds no model turn, no subscription slot and spends nothing. The agent is always told before it is stopped and given a grace period of 2 minutes by default; anything still running after that is stopped and the agent is told on resume. People see in their inbox which questions are holding an agent up.

How an agent gets its model

  1. An agent has an execution config: its system prompt, one model profile and one model name. Without it the agent cannot run. The system never picks a default.
  2. A model profile is an ordered pool of 1 to 64 provider connections. Each connection is one subscription, API credential or cloud identity, registered once for the organization.
  3. Each office holds its own binding for a connection: the private credential, never shared and never in Git. Two offices can bind the same connection and then share its quota.
  4. When a turn starts, the office freezes the pool order into the turn and walks it: skip a connection that is not ready, full or cooling down, and ask HQ for a permit on the first that fits. If that connection fails mid-turn in a safe way, it moves to the next one for the same model.

Designed (organization data documents 11 and 14). The system architecture page shows the full turn.

04Domain model

The selected relationships from docs/design/organization-data. Readable references such as T-B37 are labels; every record's identity is an immutable stable ID.

  • One home team, one lead per teamEvery employee belongs to exactly one team. The team lead is a direct member of that team and manages everyone else in it and in every team beneath it, including the leads of those sub-teams. No other member gets authority from where they sit. A separate, optional reports-to line between two people covers exceptions.
  • Accountable team is requiredThe accountable team is the one answerable if the task does not get done. It is not necessarily the team doing the work. For a project task it is the project's owner team.
  • Who does the work is separateAssigned team and assignee say who is working on it. Either can be outside the project and outside the accountable team. They are an optional pair, replaced together. Assignment never moves a file, renumbers, or grants access.
  • One task entityBugs and requests are task types. Changing type never changes ID or number.
  • Offices place agentsTeams, projects and counters belong to the organization. An office only hosts agents and caches data.
  • Repositories are sharedRegistered once per organization. Each project link carries its own integration branch.
  • Status is dataTask and feature status are stored values that an authorized person or agent sets. Nothing changes status automatically in v1; see "no transition engine" below.
  • Models are explicitAn agent runs only with an execution config that names a model profile and model. The system never picks a default.

What "no transition engine" means

A transition engine is code that decides which status changes are allowed, who may make them, and what happens automatically as a result. Examples: a task cannot become done without a review; a feature becomes live when its last task closes; closing a parent closes its children; a checklist must be complete before a status change.

The earlier design had several of these (triage, Undo, checklist promotion, automatic feature transitions, request approval). v1 does not carry them over. In v1:

  • An authorized person or agent sets a status to any valid value.
  • The change is recorded in the task's history with who made it and when.
  • Nothing moves on its own. The one guard is that a feature in progress or live must have an owner.

The reason is scope. Each engine is a product decision with its own rules, and carrying them over silently would lock in behaviour nobody chose for the new model. The valid status words still need to be published so every screen and agent uses the same ones.

Processes and standards

Processes (how we do something) and standards (rules work must meet) are first-class records. The organization has a set, every team at any depth has its own set, and every project has its own set.

  • Selected for v1: the files, their scope, their lifecycle and owner, and the override lock. A lock set at a higher scope cannot be defeated by an edit lower down.
  • Selected for v1 on 2026-11-17: resolution, meaning which documents apply to a piece of work. Start with the organization's. Apply the accountable team's chain from the top team down. Then the project's. A lower level may add a document, or replace one from above with the same key, unless the upper one is marked not overridable.
  • What the agent receives: first the product's built-in instructions on how to work in the system, the same for every agent (agent-instructions.md). Then every non-overridable document is always included, in a marked section of the agent's system instructions that says it must be followed. Overridable documents are guidance the agent applies with judgment. Guidance on the product's own commands ships as built-in skills.
  • Not selected: mechanically blocking an action that breaks a process, and approval workflows.

Because an employee has one home team and a task has one accountable team, there is one chain and nothing to reconcile between teams. The org-process library implements an earlier, more complicated rule and has no caller yet; it is to be simplified and called when an agent is launched.

05Where truth lives

The design separates sources from caches, because that decides what a backup must contain and what can be thrown away.

If you loseYou can restore fromYou cannot recover
The office databaseOrganization Git plus the operational sources. Rebind credentials, reconcile processes.Nothing, if the sources are intact.
The operational sourcesA valid backup with verified identity, epoch and digests.Anything after the backup. Gaps must be disclosed.
Sources and backupsOrganization Git restores published definitions, open work, published task history, and every number allocated up to the last publish.Chat, receipts, usage history, budgets, and numbers allocated since the last publish.
Host custody (keys)Not supported. Startup never recreates a missing key.The encrypted databases it protected. This is a direct cost of encrypting; see below.

Git publication is hourly and asynchronous. It is a publication target and never the point at which a change is acknowledged. A machine restore needs the unpublished journals too.

Numbering is already in Git. Counters and every allocation are files in the organization repository (identity/counters/, identity/allocations/) and go out with the hourly publish. Allocations made since the last publish exist only in HQ's durable/ (its files and acceptance journal). If those are lost, allocation pauses until a safe high-water mark is established; a number is never guessed from the open tasks.

Task history: what it is and what it buys

A task file holds the task as it is now. Task history is the list of changes that got it there: one small JSON file per accepted change, at work-history/tasks/<task-id>/<revision>.json. Each records what changed (created, assignment, status, a comment, a link), the old and new values, who did it and when.

It is separate from the task's own fields because the current state cannot tell you how it got there. Three things depend on it:

  • Accountability. Who reported the task, who reassigned it and when, and what its status was on a given day, still answerable after the task is closed or archived.
  • Rebuilding. An office database rebuilt from files gets the same history back. Without the files, history would live only in a cache the design calls disposable.
  • Safe retries. Each change has a revision number, so a repeated or conflicting change from another office is detected and never silently overwrites.

If history were lost, the tasks themselves and their final state would survive; the record of who did what and when would not. Whether that history belongs in Git, or should stay as a local protected source and be published in a more compact form, is a fair question.

Encryption, explained by who can still read the data

There are three different protections, and they stop different people. The third one is "application-level encryption".

ProtectionWhat it doesWho can still read the data
Disk encryption (FileVault on a Mac)Scrambles the whole disk. It unlocks when the machine is on and someone is logged in.Every program running on the machine. It only protects a machine that is stolen or switched off.
File permissionsThe operating system refuses other user accounts access to the files.Any program running under the same user account.
Application-level encryption (SQLCipher)The contents of the database file itself are scrambled. A program needs the key to read it, even if it can open the file.Only a program that holds the key. Here that is the office worker, which gets it from the host.

The third one exists here for one main reason: today agents run under the same user account as the server. File permissions therefore do not stop an agent. An agent can run shell commands, and if one got past its tool restrictions it could open the database file directly. With application-level encryption that file is useless to it, because the key is held where an agent cannot reach it. A second, smaller benefit is that a copied or backed-up data folder cannot be read elsewhere.

The costs are real: the host must be a signed program with special permission to reach the key or it refuses to start; Linux had no agreed place to keep the key; and a lost key means lost data with no way back.

This is why your suggestion matters. If agents run as a different user account, plain file permissions do the job, and application-level encryption loses its main reason to exist.

Running agents apart from the data

The current design runs agents as the same user and relies on each vendor tool's own sandbox for the commands it runs, plus the office approving or denying actions. The design says plainly that sharing a user is not isolation and that separate users or containers are the stronger option, left for later. There are four levels, and they can coexist.

LevelWhat it isWhat it needsLimits
0 · Tool sandbox only (today's design)The vendor tool restricts the commands it runs. The office approves or denies.Nothing.The vendor tool itself is unrestricted and runs as the same user as the data.
1 · Operating-system sandbox, same userThe whole agent process and everything it starts runs inside an OS sandbox that denies the data folders.No administrator rights.On a Mac, a sandboxed program generally cannot start another sandbox, and the vendor tools and Swift's build tools start their own. This needs a test before relying on it.
2 · Separate user accountAgents run as a dedicated account that owns only their workspaces. The data folders are closed to it by ordinary permissions.One administrator step at install, and a small launcher to start and stop agents.For iOS work, Xcode signing identities, simulators and the vendor sign-in belong to a user's own session, so they must be set up for that account.
3 · Container or virtual machineA fully separate file system.A container runtime, or a virtual machine.Cannot use the host's Xcode directly, so not for iOS builds.

A separate user is not a re-architecture. The shape stays the same: the office starts each agent through the process library. Four things change:

  • The launch description gains an isolation setting. Today it carries only program, arguments, working directory and environment.
  • A small privileged launcher is installed at setup, because an ordinary program cannot start or stop a process that belongs to another user. Start, stop and cleanup go through it.
  • Agent workspaces are owned by, or shared with, the agent account. The data root is closed to it.
  • Each vendor sign-in is stored under the agent account, which fits the selected rule that credentials are bound per office.

Keeping it extensible. Isolation becomes a named, replaceable part of the launch contract, chosen per agent. An agent that builds iOS features can run at level 0 or 1 while the others run at level 2, and a container level can be added later without touching the rest. The execution contract already requires every runtime to declare which isolation it supports.

A private home for every agent

Decided 2026-11-17 (ADR-0015 decisions 10 to 12). Each agent gets its own home directory, created and controlled by the office. The vendor folders an agent tool looks for, such as ~/.claude, are redirected into it. The agent sees a vendor folder that contains only what the office put there: the office's settings, the agent's own transcripts and one sign-in. Your own vendor folders are never read or written by an office-run agent.

Where the sign-in comes from. From the subscription pool. For each launch the pool selects a connection, and the office makes that connection's sign-in available inside the agent's home. Moving an agent to another subscription is a controlled relaunch.

Is changing the root directory (chroot) a cheap sandbox? I evaluated it. It needs administrator rights on both systems, and on a Mac it is not workable: tools, compilers and Xcode need the system volume, which a changed root hides. The same protection is available another way on each system: a private mount view on Linux, which needs no administrator rights, and a sandbox profile on a Mac that denies everything outside the agent's home and workspace. That is level 1 in the table above, recorded as the reserved os-sandbox mode. The private home gives you the "virtual folder" now; the stronger wall is a later mode, not v1. One test is needed first: how each vendor tool is pointed at a relocated sign-in, and where a Mac's Keychain entry is looked up.

macOS and Linux, including containers

Decided 2026-11-17 (ADR-0017). Both systems are v1, and an office can run inside a container. Today the host starts office workers only on a Mac. The differences are put behind five small contracts, each with a Mac and a Linux implementation: checking that a started program is the one intended, where the host keeps its secrets, confining the web process, how the service is started and restarted, and agent isolation. Nothing else may branch on the operating system, and a missing piece refuses to start instead of running unprotected. One honest limit: Linux has no equivalent of a Mac's code signature, so that check is weaker there against someone who can already replace files as the service user.

Decided 2026-11-17. Two decisions.

Isolation (ADR-0015). Isolation is a setting in the launch contract with two v1 values: the same user as today, and a dedicated user, one per instance, that setup creates with one administrator step. The office's local socket will also admit that account; today it admits only its own user. If setup has no administrator rights it carries on in same-user mode and says so. An agent set to the dedicated user is never quietly started as the same user. A short test on a Mac comes before the dedicated user becomes the default.

Encryption (ADR-0016). Application-level encryption is removed. Organization data is protected by disk encryption, file permissions and the isolation setting. In same-user mode that means the vendor tool's sandbox and the office's rules are all that stand between an agent and the data, and the product will say so.

Private keys stay protected, by your choice of 2026-11-17. Secrets are different from data. An office holds a few private keys: the organization's certificate authority key today, and later each office's TLS identity key and the key used when inviting a new office. They stay in the office's own store, each one encrypted with a single key per office that the host keeps and hands over at start-up. The host never sees the private keys themselves. If that one key were lost, the office would still open all its data; only the functions that need a private key would stop, and each key can be recovered or reissued. The cost is that one host-held key per office remains, in a much smaller role than before.

06Rules everything aims at

These are the invariants repeated across the ADRs and data contracts. A change that breaks one needs a recorded decision.

  • The browser is a clientClients never open SQL. All state changes go through the office worker. ADR-0001.
  • One writer per databaseOne write connection on one thread. Transactions, deduplication, outbox and sequence allocation stay atomic. ADR-0002.
  • Keys stay with the hostThe worker receives its key at launch. The worker and web process never touch a key store.
  • Files are canonicalSQLite is an indexed projection. A valid row is never launch authority or an authorization grant.
  • Acknowledge after durable evidenceA command completes only when its journal record is readable. ADR-0006.
  • HQ is the authorityOffices never increment shared counters. Numbers are allocated once, in one serialized place, and never reused.
  • Stable IDs never changeUUIDv7, the published standard (RFC 9562). The newer HQ-creation code already uses it; the rest uses ULIDs and is to change.
  • Every mutation is idempotentOne operation ID per intent. An unknown outcome is resolved by lookup, never by a fresh ID.
  • Credentials stay office-localNever in Git, command payloads, journals or logs. Agents never hold a push token.
  • Fail closed, no mocksA missing capability shows unavailable. Missing trust or platform support refuses to start.
  • Nothing promotes itselfNo automatic failover. A restored office or stale authority is fenced by epochs and generations.
  • Apps compose cratesLogic lives in libraries, binaries stay thin, no source cycles, domain modules contain vertical slices.

Why one writer, and can the database be replaced later?

Is one writer efficient? For SQLite, yes. SQLite itself allows one write transaction at a time, whatever the language. Several write connections would only queue on its lock. One dedicated writer that batches is how SQLite gets throughput: many commands share a single flush to disk. Reads are not affected; they run in parallel on their own connections.

What else the rule does. It also makes ordering simple: allocating a sequence number, checking for a duplicate and writing an outbox entry happen together or not at all. That guarantee is the part worth keeping under any database.

Could it move to PostgreSQL later without a re-architecture? Mostly yes, and the code is already shaped for it:

  • SQL lives in two crates only: org-office and org-host. The domain crates (org-work, org-mailbox, org-sync) contain no SQL. They define the storage operations they need, and the store implements them.
  • Inside org-office, 23 of the 26 files that use SQLite sit under its private store folder. That is about 14,700 lines, but it is not one file: it is split by area, as the table below shows. Its first line states the rule: "The only module that knows SQLite … replacing the engine means replacing this file and its submodules."
  • The domain crates reach storage through small interfaces (WorkStore, MessageStore, OrgStore), so a second implementation can sit beside the first. Replication also has a test suite that is independent of the engine, which a new engine would have to pass.
  • In the selected design the database is a rebuildable index of files, which lowers the stakes of changing it further.

With PostgreSQL the single connection would no longer be needed; the ordering guarantee would come from transactions. Decided 2026-11-17 (ADR-0018). PostgreSQL must be possible later, so the rule is written down now: only the storage adapters know which database is in use; the guarantees are stated without naming a database; the store is chosen at one place at start-up; and every storage contract gets a test suite that any database must pass, as replication already has. The contract wording no longer names a database statement. The code work is to move the two stray files behind the store, add the selection point and write three suites; messaging and replication already have one. It is best done together with the storage rebuild, which touches the same code.

Task numbers come from the office that creates the task

Decided 2026-11-17 (ADR-0019). You asked that creating a task never waits for HQ, because tasks are what agents create all day.

  • The reference is T-, the office's letter, and a number. HQ is A, the second office B. HQ's first task is T-A1; the second office's thirty-seventh is T-B37.
  • Each office counts all its own tasks in one sequence, whatever project or team they are in. So T-B37 is unique in the organization and complete on its own; it never needs a project in front.
  • The office numbers the task itself, in the same local save. No round trip to HQ, online or offline, and a task never shows "Pending number".
  • The reference never changes: not when the task is reassigned, moved to another project, or when the agent moves to another office. The letter says where the number was made, not where the task lives.
  • Never reused. An office keeps a durable mark above the last number it used. If an office cannot prove its sequence, for example after being restored from an old backup, it gets a new letter from HQ before it creates another task.
  • Tasks only. Teams, projects, features, releases and milestones are created less often and keep their numbers from HQ. A feature created while HQ is unreachable is usable by its permanent ID and shows "Pending number" until HQ registers it.

Which project a command means. Finding a task by its reference never needs a project. Commands that do need one, such as creating or listing tasks, take it from the agent's context: agent-os knows the project of the task the agent is working on, or the project the agent is assigned to. If the agent has no project, or means another one, it must say which.

Creating a task is fast. Decided 2026-11-17: creating a task uses the fast acknowledgement. The office answers once its database has the task and flushes to the drive just after. That is safe for numbering, because the durable mark prevents a number from being given twice.

What the gap looks like

The libraries are deep and the entry points are closed. Three things are true at once:

  • No shipped path creates an organization. agentic-org setup refuses, and host.sock answers only hello and a status count. Organization creation is exercised from tests.
  • No shipped path reaches the browser. The web binary refuses to listen, and the production UI build has no backend adapter.
  • No code launches an agent. There are no runtime adapters, no model routing, no usage ledger and no Git operations.

My reading of the dependency order. The three Blocked rows chain together: HQ bootstrap (FC-012) unlocks the production browser service (FC-013), which unlocks sign-in (FC-014). Domain screens need those. Separately, the usage ledger (FC-084) gates every cost and budget row, and runtime adapters (FC-101) gate execution. This ordering is inferred from the checklist, not stated in one place.
