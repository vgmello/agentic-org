01Process topology

One named instance runs as one OS user. The service manager starts the host; the host starts everything else. There is no separate host daemon, updater or supervisor daemon.

Naming. This page says web for agentic-org-web. The design documents now say web too (the browser API design is web-api-v1.md). Some code identifiers still say gateway, for example ChannelKind::Gateway; renaming them is decided and still to do. There is no model gateway.

agent-os speed. ADR-0003 section 5 targets a same-office send at p50 under 15 ms: about 2 ms to start the process, 0.5 ms to connect, and 6 to 10 ms waiting for a full flush to disk. Measured on a Linux build machine, starting a do-nothing program takes about 1.1 ms and agent-os --version about 1.5 ms, so a 1 to 2 ms budget cannot include a process start. A database commit measured 0.013 ms without waiting for the drive and 0.29 ms with it. Decided (ADR-0014): messaging and non-critical task activity are acknowledged once the database commits, with the flush following; the class is declared in the domain crate and honoured by the store adapter, so it does not depend on the engine; and agent-os gains a long-running mode per agent session; target median 1 ms. The Linux binary is 1.56 MB against a 1 MB target.

Same user is not isolation. Every process runs as one OS user. The design says so explicitly and relies on code-signature checks, sandbox profiles and file-descriptor handoff instead of user separation. The host can only spawn workers on macOS today; other platforms return "office servers run only on macOS".

Frame and version facts

  • Local frames are UTF-8 JSON, one object per line, at most 1 MiB. A request has an id; an event has event and no id.
  • org-proto declares API_VERSION = 1 and supports versions 1 and 2.
  • There is no WebSocket, no server-sent events endpoint, no mutual TLS and no HTTP client in the code.
  • CLIs parse arguments by hand. There is no argument-parsing library.

How the layout is meant to evolve

The target is application → domain module → feature. A crate is a packaging and visibility boundary; a module is a cohesive capability; a feature is one use case with its validation, persistence and tests kept together. One feature does not imply one crate.

Can the storage engine be replaced?

  • SQL exists in two crates: org-office and org-host. The domain crates define storage ports and contain no SQL.
  • In org-office, 23 of 26 files that use SQLite are under the private store folder. It is split by area: engine and single writer (1,900 lines), organization with replication and snapshots (6,400), accepted-write journal (2,700), work (1,500), messages (800), other (1,400). Two files outside it also use SQL: organization/bootstrap.rs and organization/admission.rs; messaging.rs uses it only in tests.
  • Domain crates reach storage through WorkStore, MessageStore and OrgStore, and replication has an engine-independent conformance suite. A second engine means a second implementation per area and making the store selectable at start-up.
  • The single writer does two jobs: it fits SQLite's one-writer engine, and it keeps sequence allocation, deduplication and outbox writes atomic. Only the second must survive a move to another database.
  • What ties the code to SQLite today: those files outside the store and the database encryption, which is being removed.

Database rules that hold in both shapes

  • SQLite through rusqlite. WAL, synchronous=FULL, full fsync. No application-level encryption (ADR-0016); today the build still bundles SQLCipher with a raw key, which the plan removes.
  • One write connection on one thread per database, batching with savepoints. Readers use a small pool.
  • Schemas are versioned in code by user_version. There are no SQL migration files.
  • The host creates each office key once and never recreates it. A missing key is an error, key_missing.
  • The draft target schema is 89 tables and 11 views. It is a structural draft, not an applied migration. Every write connection must enable foreign_keys and recursive_triggers.

The newer HQ-creation path in the host already mints them; the rest of the code mints ULIDs and is to change.
  • A task is numbered by the office that creates it, in the same local save: T-, the office's letter, and the next number of that office's one sequence. It is never unnumbered and its reference is unique in the organization on its own.
  • A feature created while HQ is unreachable is saved with number: null. The organization authority allocates HQ numbers in one serialized transaction. No client ever computes MAX + 1.
  • A task has a status from one closed list (todo, in progress, blocked, cancelled, done; done or cancelled is finished), a priority (urgent, high, normal, low) and, optionally, an effort in whole points.
  • Gaps are allowed and numbers are never reused. A type change, a reassignment or a move to another project or office never renumbers.
  • A task reference needs nothing in front. HQ-numbered records are qualified outside their scope: P-8/F-6, P-8/R-3/M-2.
  • Commands that need a project, such as creating or listing tasks, take it from the agent's context; an agent with no project, or meaning another one, must name it.
  • schema_version is the file format. revision is the record's concurrency revision. A task event is identified by organization, task and revision.
  • There are no old references to map. Nothing has shipped, so bugs and requests are typed tasks from the start (owner decision 2026-11-17).
  • HQ gives each office its letter when it creates or enrols the office; a letter is never changed or reused (ADR-0019).

Today the code uses ULIDs and per-kind, per-project number scopes with task.assign. The typed-task identity, UUIDv7 and office-made task numbers are pending.

Offline offices

  • A task created offline has its final reference at once. A feature created offline is saved with its permanent ID and an empty number, shown as "Pending number".
  • The feature is fully usable by ID. On reconnect HQ allocates once; the number is added and never changes.
  • Counters and allocations are files in organization Git (identity/counters/, identity/allocations/), published hourly. Allocations since the last publish live in durable/authority/numbering-journal/.
  • Each office keeps its own task counter with a durable mark above the last number used. An office that cannot prove its sequence gets a new letter from HQ before it creates another task (register entry C-12).

06Browser request path

How a person's action reaches the writer and how the browser learns the outcome. Built, not reachable for the HTTP stack and contracts; the office side of it runs today over the local socket.

  1. Browser → webPOST /api/v1/session/sign-in. The web process asks the host to verify the account. The response sets the cookie and returns the session proof.
  2. Browser → webA mutation carries a ULID operation_id, a scope, typed parameters, the cookie and the proof header.
  3. WebValidates the cookie and proof pair, origin, path and scope. Decodes strictly. Maps the one operation ID to the native command ID.
  4. Web → officeSends the command on its host-granted channel with the human principal and grant. The web process never sees a database key.
  5. OfficeAuthorizes against its own rules and commits through the single writer.
  6. Web → browserClassifies the outcome: completed (200), accepted (202), rejected, or unknown (504).
  7. Browser → webAn unknown outcome is resolved by GET /api/v1/operations/{kind}/{id} with the same ID. A fresh ID is never minted for a retry.

What the browser may assume

  • Browser state is a view of server authority, with explicit loading, unavailable, error and freshness states.
  • Acceptance of a command does not prove completion, and completion does not prove an agent read it. The UI shows command outcome and runtime delivery separately.
  • A command to an office known to be offline is rejected before admission, with nothing queued. Pause is the exception: it is a durable HQ status command with the runtime stop pending until acknowledged.
  • Closing the browser never ends durable work.
  • Authoritative validation and authorization happen in the office. Client validation is feedback only.
  • Sessions are in memory in both the web process and the host today, so any restart signs every browser out with a generic "session ended". Same-account sign-in keeps typed drafts; nothing is re-sent automatically. Decided 2026-11-17 (ADR-0013): sessions will be stored at the host as digests, cached in memory by the web process and re-checked once after a restart, so restarts no longer sign people out. Signed tokens are a v2 option.

07Accepted writes

The rule for when a change counts as saved. It is selected first for task assignment (ADR-0006) and is the pattern the other durable sources follow.

  • One office writer allocates both the journal ordinal and the work-origin position. A fork or gap in the chain stops recovery.
  • Snapshot, event and idempotency result commit as one recoverable operation before the acknowledgement.
  • A matching terminal receipt returns the original outcome. The same operation ID with a different payload is a conflict.
  • New task events use codec 2: canonical JSON with a SHA-256 of the payload. Older bytes are never re-encoded.
  • SQL triggers block update, delete and replace on task events.

Built, not reachable The durable acceptance journal, native replay and legacy capture landed on this branch as foundations (the selected_* tables in office.db schema 8). HQ creation persistence and admitted bootstrap landed in the latest merge. The selected-task routes that would drive them from the browser are on an unaccepted branch.

08Agent execution

The supervisor, connection router and session runner are internal parts of the office worker. There is no separate supervisor process.

Rules of the turn

Admission

  • The first release accepts explicit turn commands only. There is no scheduler and no queue. A second open turn returns BUSY.
  • An agent without an execution config is not runnable. The framework never chooses a default model.
  • RunTurn names turn, employee, placement generation, expected config and profile revisions, task or none, workspace, and an immutable input reference with its hash.
  • No discovery, Git fetch or sign-in flow runs on the dispatch path. Stale evidence means skip and refresh in the background.

Failover and recovery

  • Failover keeps the same target model and tries each eligible connection at most once per cycle. Exhaustion gives POOL_EXHAUSTED and a blocked turn.
  • Retry-eligible errors: rate limited, quota exhausted, auth expired, model unavailable.
  • Replay only when no effect is proven. Resume only from a verified checkpoint with tool receipts. Otherwise RECOVERY_REQUIRED, keeping the slot and workspace.
  • Message sends, commits and deploys count as effects. Brokered tools have durable receipts.

Process ownership

  • One open turn and one main process per employee.
  • Planned ownership is fsynced before spawn; PID, start time and boot identity before input.
  • A process is never signalled from a restored PID alone. Ownership mark, generation, boot and start identity must all match.
  • Recreating an office database does not authorize starting another copy of an agent. Placement generations fence that.

What is in the code

  • org-runtime: the port, a sans-I/O session, launch plans. Implemented only by a test double.
  • org-supervise: real spawn, stop, cleanup and orphan recovery. The office uses only its recovery record types, from tests.
  • spikes/claude and spikes/codex: research evidence for claude -p stream-json and codex app-server.
  • The worker source says it plainly: "No child-spawn paths exist today."

A successful turn does not close its task. Task status stays a separate authored value.

What the agent is told at a start Designed

The office composes an agent's instructions before every start, the same way for every runtime. They carry the employee's identity and role, its prompt, the objective of the turn, every non-overridable process and standard in full, and summaries of the overridable ones. When the task's project follows a development process (section 15) they also carry a short block naming the project's process, its stages and the agent's role in it, and the title and when-to-use line of each skill written for that role or for everyone. A skill body is retrieved with agent-os process show <key>. The vendor tool's own skill loading stays switched off; the development process is the one source. Who starts a turn does not change: an explicit instruction from a person, the answer to a required ask, or a recovery.

09Providers, usage and budgets

Three control contracts wrap execution: which route a turn may use, what it cost, and whether more work may start. All three are Designed.

Provider connections and pools

  • A provider connection is an organization-wide route for one subscription, API credential or cloud identity. There is exactly one per subscription identity; a second office binds the same connection and shares its quota.
  • A model profile is an ordered pool of 1 to 64 connections. Creating a connection also creates a single-member default profile.
  • Each office keeps its own binding (the private credential reference), readiness state and discovered models. Models are discovered, with no global catalogue.
  • Probes run at startup, on binding change, on refresh, and every 60 seconds while in use. Evidence is valid for at most 300 seconds.
  • HQ is the single permit and cooldown coordinator. A permit lasts 60 seconds and renews every 10. A rate limit cools the whole connection for Retry-After, or 900 seconds.

Usage and cost

  • Each accepted report is one immutable usage event: input, output, cache-read and cache-write tokens. Null means unknown; zero means known zero.
  • Cost is integer micro-USD and always an estimate. Price versions become immutable once referenced. Old events are never repriced.
  • Events append to JSONL at durable/accounting/usage/<origin-office>/<producer>/<date>.jsonl, with a checkpoint published before the capture is acknowledged.
  • Attribution is a snapshot taken at consumption time. Reassigning a task never moves past spend. Corrections append a superseding event through the organization authority.
  • Totals per task, agent and project are derived views. Nothing is incremented on a parent, and totals carry incompleteness counts.

10Messaging

Agents and people are the same kind of participant. Routing is office first, then through HQ (ADR-0003).

  1. agent-os → its own officeBinds with its session token and sends.
  2. OfficeChecks the recipient against its applied organization position, commits the message, and allocates an origin sequence in the same transaction.
  3. Office, same-office recipientWakes the recipient in memory at once.
  4. Office → HQ → recipient's officeOtherwise the change streams to HQ. HQ deduplicates by origin office, incarnation and sequence, acknowledges, and forwards. People and the owner are owned by HQ.
  5. Owning officeAn ask carries an expiry with at most 2 seconds of clock skew. Late arrivals expire. Only the owning office dead-letters and emits delivery_failed.

Selected data model

  • Conversations of kind DM (two members), group DM (at most eight), channel, and imported directed thread.
  • Threads live inside one conversation. Cross-conversation replies are rejected.
  • Asks and approvals are versioned cards in message metadata. Only the addressed actor may answer.
  • The per-recipient inbox is recipient state: unread, snoozed, read, done, expired, dead letter.
  • Visibility is checked per actor on every read, search and attachment access.

State

  • Runs today agent-os over its file queue, and send, inbox, read, wait on the office socket.
  • Built, not reachable ask, reply, defer, done, notify and threads are defined in org-proto and not served by the office.
  • Designed protected envelope sources, channels, cross-office relay, and required asks that suspend and resume an agent.

Send and ask (ADR-0014, decided 2026-11-17). A plain send answers once the sender's office has saved it locally, in single-digit milliseconds in every topology; relaying to another office happens afterwards and is retried. An ask holds its caller, always has a deadline, and returns a timeout when it passes. Each messaging file has one writing office: a message is written once by the sender's office, and each employee's read state, reactions and preferences live in that employee's own files.

Asking and waiting (ADR-0020, decided 2026-11-17). An ask waits for a bounded time, an organization setting that is the same for a person or an agent, and carries required. Not required and unanswered: the ask returns a timeout and the agent decides. Required and unanswered: the office tells the agent to wind down its background work, gives it a grace period, stops its process and releases its turn permit and subscription slot; the question stays open. When the answer is committed, the office resumes the same session with the answer as the next input, through the normal start checks. The office keeps a durable record of each suspended agent, so a restart loses nothing.

11Git and repositories

The office runs all network Git. Agents work in a local worktree and never hold a push token. Designed; there is no Git code in the workspace.

  1. HQRegisters a repository once in repositories.yaml (remote or local), then links it to a project with an explicit integration branch.
  2. OfficeClones one bare cache per repository on first need: runtime/<office-id>/repositories/<repository-id>.git.
  3. OfficeOn assignment, creates a worktree on task/<ref>-<slug> from the link's integration branch, under the employee's path.
  4. AgentWorks and commits locally. Commits are authored as the owner with the agent as co-author.
  5. Agent → agent-os → officeRequests a push. The office pushes the task branch. Never the default branch, never a force push.
  6. OfficePushes with its own Git credential for that remote. Agents never hold a credential that can push.
  7. PersonOpens any pull request and merges. Provider integrations (an app, short-lived tokens, creating repositories, pull requests by agents) are v2.
  8. PersonReviews and merges. Merging in-product is a later decision.
  9. OfficeAfter closure and merge: tags merged/<branch>, deletes the remote task branch by compare-and-swap, removes the worktree. A handoff never triggers cleanup.

Two kinds of repository are easy to confuse. The organization repository holds definitions and must be remote. Code repositories hold product code and may be local only.

Development processes and each project's documentation tree are organization repository content (section 15). A document is never written into a code worktree. A code link points the other way, from a document to a path in a code repository; its stale check reads the office's verified cache at the link's integration branch and needs no network.

12HQ and satellites

A satellite is the same worker binary on another machine. It connects out to HQ and never listens publicly.

Enrolling a satellite

  1. Owner at HQCreates an invitation.
  2. Destination hostReceives office.join on its host.sock and starts a worker.
  3. Destination workerGenerates its TLS key, pins HQ's office ID and CA fingerprint, and signs the TLS exporter with the invitation key.
  4. Owner at HQApproves an 8-character check code.
  5. HQIssues a one-year certificate and sends the snapshot. The office becomes active after initial sync.
  • Sync is deterministic apply at (epoch, seq), with snapshot replace. The per-origin work stream is deduplicated by office, incarnation and sequence.
  • The command outbox is ordered and separate from the message queue.
  • Promotion of a satellite to HQ is manual and deferred. Higher observed epochs fence stale authority.
  • Setup creates no office. The HQ office is created with its organization, from the browser. Satellite onboarding is a separate flow started from HQ and is unavailable today.

Boundary rules

  • The web process and agent-os get scoped capabilities only. Neither gets host key access or a database key.
  • An employee token is not host administration authority.
  • Browser authentication and federation TLS are separate boundaries.
  • A SQL row is a projection. It is never launch authority, and raw SQL access on a replica establishes no authority.
  • No field on a record grants authority. The owner is a person; being the owner is a permission of their account at the host. Exactly one account is the server's administrator. Private task notes are hidden even from owners and the administrator.
  • Channel capacity is bounded: 8 per office, 7 for the web process, one reserved for local use. A capacity refusal is ordinary; a malformed transfer is fatal.
  • Tests never write to a user's organization workspace and never touch the installed live CLI or spool.

14Install, release and recovery

First run: install, register, create the organization Designed; creation is Built, not reachable; setup refuses today

  1. Bootstrap → setupDownloads and verifies agentic-org, then runs setup, or setup --bundle <path> --offline.
  2. SetupVerifies the complete signed release: an Ed25519 signature over the manifest covering four executables and the UI. Publishes it atomically and pins it (ADR-0009).
  3. SetupReserves the instance, registers and starts the service, and prints one registration link. The host keeps only a digest of the link's token. Setup asks for no username or password and creates no account, organization or office.
  4. Browser → web → hostThe person opens the link and chooses a username and password. The host redeems the token once, creates the account and marks it as the server's one administrator.
  5. Browser → web → hostThe administrator creates an organization: name, slug, remote organization repository and state branch. No team is asked.
  6. HostStages the recovery code in its credential provider and keeps only an opaque handle.
  7. Host → officeCreates the office secrets key and launches the HQ worker with an HQ-creation context and the code.
  8. OfficeGenerates the CA key, seals it (Argon2id, AES-256-GCM), and commits key, envelope and completion in one transaction. Publishes the public envelope. Drops the code. A retry reuses the same material (ADR-0007).
  9. OfficeIn the same accepted transaction: the organization, one top-level team named after it, the creator's person record in that team as its lead, and the built-in HR employee. The creator's account owns the organization.
  10. Server machineThe recovery code waits to be collected with agentic-org recovery release, at the machine, after device-owner authentication. It is never shown in the browser.

An offline setup makes no external requests. The account created from setup's link gets its person record when it creates the organization.

Accounts Designed

  • Accounts, their password verifiers, sessions and one-time links are host data. Links are stored only as digests, work once and expire.
  • Exactly one account is the administrator. agentic-org admin reset, on the server machine, is the only account command: it issues a new one-time link for that account.
  • Every account is tied to exactly one person in each organization it can open, and an account is never tied to an agent. The link between account and person is host data; it grants nothing by itself.

How people are invited and what each screen shows is in docs/specs/server-installation-and-access-ux.md.

Opening an existing organization Designed

Accounts, sessions and the list of organizations live only in the host's database. If it is lost, the administrator registers again with agentic-org admin reset and opens each organization from its files: the host registers it under its existing ID, the office rebuilds its database from the files and starts a new incarnation, the administrator chooses their person record and becomes the owner, and people are invited again. From the repository alone, everything published comes back; chat, usage, budgets and private notes come back only if the data folder survived or from a backup. Invalid files refuse the open and are named; nothing is guessed.

Updates Designed

A person installs only agentic-org; it installs and updates everything else and itself. A release is always complete: four executables and the UI under one signed manifest.

  1. HostChecks for a new release in the background under the configured policy. An unreachable source never blocks startup.
  2. HostStages and verifies the complete release into an immutable versioned directory.
  3. HostDrains the instance under its maintenance policy, stops it, applies supported data-format changes, switches the pin.
  4. Service manager → hostRestarts serve from the newly pinned agentic-org, which starts the new worker and web process and probes readiness.

The prior release and a recoverable data state are kept. An executable is never rolled back alone after an incompatible data change. agentic-org upgrade runs the same steps on demand. Pins are per instance. The web restart signs browsers out.

Recovery code delivery Designed (ADR-0011)

  1. Administrator → CLIRuns agentic-org recovery release at the HQ machine, on a terminal.
  2. HostVerifies the signed peer, console session and foreground terminal. Prompts for device-owner authentication once.
  3. HostCommits the delivered state and a code-free audit record, then prints the code to the terminal only.
  4. AdministratorTypes the final code group and confirms. The host deletes the pending code and marks it acknowledged.

What recovery covers

  • There is no automatic failover and no automatic HQ promotion. A restored office never promotes itself.
  • Restoring host custody and moving an office between machines are unsupported until verified fencing evidence exists.
  • Backup automation and restore commands are not selected. Backups must include the operational sources and separately managed credentials.
  • There is no legacy data to adopt: nothing has shipped, and ADR-0010 is withdrawn.

15Development processes and project documentation

How a project is given a way of working without the product knowing any methodology, and where a project's documents live. Designed on 2026-11-18 from the owner's REQ-06 and REQ-07; nothing is built. The records are in document 18 of the data contract.

What a development process is, and what it is not

Content

  • A folder in organization Git, development-processes/<process-id>/: a manifest, a definition per role, skills and document templates. Parts are named by key inside the development process.
  • The manifest declares roles (a few marked seed), document kinds (some versioned), the folders a project's documentation starts with, and stages that describe the order of work.
  • A built-in development process ships with the product, has a fixed ID and no file, and cannot be edited. An organization changes one by copying it. The first is dss.

Limits

  • No engine. Nothing reads a stage, starts work because a document changed, or blocks an action.
  • A development process grants nothing. It names no tool, model, credential, budget or approver, and an unknown manifest field is refused.
  • A skill is overridable guidance. It is never must-follow text and never displaces a document marked overridable: false.

Roles and skills

  • A development process role is matched to an organization role by key. Missing ones are created when the development process is chosen; existing ones are left alone. An employee still has one role.
  • Resolution gains one layer: organization, the accountable team's chain, the project's development process, the project.
  • An agent receives the skills whose roles name its role's key, and the ones written for everyone. A project document with a skill's key replaces that skill in that project.

Hiring

  • The seed roster is derived: a seed role is filled when an active member of the project's team holds it.
  • A skill tells a lead when to staff. The lead reads the role (agent-os role show) and asks (agent-os hire request --role).
  • HR drafts, a lead approves, product code provisions. A lead who is a person approves; a lead who is an agent approves only when a person has turned on its may_hire permission, and then its own request is enough (ADR-0022). A development process decides when a lead asks and gives no one the right to approve.

Calls

Calls go to the caller's own office on a bound connection. Every write carries an operation ID and an expected revision.

The project boundary for agents

People read and write the documentation of every project of their organization. An agent reads and writes the tree of its own projects only: a project whose owning team is its home team or a team above it, a project one of whose contributing teams is, and a project in which it is the assignee of an open task. For any other project the index, the listing, the files and every write are refused with not_authorized and the reason other_project, and the refusal names that project's lead. The office checks this from the agent's binding on every call. An agent that needs something from another project asks that project's agents and people.

One writing office, and limits

  • A project's tree and its index have one writing office at a time, as a task has its writer. It starts as HQ and is handed to the office where the project's agents work. An agent in that office is acknowledged locally. From another office a read is local, and a write goes to the writer through HQ and is acknowledged when the writer accepts it, like a cross-office edit of a task.
  • If the tree and the index are found to differ, for example after a commit made outside the product, the project shows a problem and the office repairs the copied fields from the files. It never deletes a file to make the two agree.
  • An issued version is written once. The draft schema refuses an update, a delete and a replace of its row.
  • A document is at most 512 KiB, so a write fits one frame. A media file is at most 5 MiB; one larger than 512 KiB is uploaded in parts first (doc.upload), and the write that stores it names the upload and its SHA-256.
  • A tree holds at most 10,000 entries. The index is returned whole up to 256 KiB and by section beyond that. A path is at most 512 bytes and eight levels deep.
  • Skills count against the same 24 KiB cap as other overridable guidance.

Open with the owner. The flows of REQ-06 and REQ-07 have one agent hand work to another, or ask another, and expect it to act. Today a turn starts only from a person's Run or the answer to a required ask. Whether an ask or a task assignment starts an agent is not decided. Until it is, a person presses Run on the next agent. Nothing in this section changes that rule.
