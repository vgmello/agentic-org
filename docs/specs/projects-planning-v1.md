## 1. The problem

**[F] The owner, 2026-11-12:**
- Projects have tasks. Any task not attached to a release is in the project's **backlog**. The backlog is a view, not a stored thing.
- **Releases** have a name and a potential date. **Milestones** sit under a release. Tasks attach to a release or a milestone.
- Every project, release, milestone and task gets a short public key, numbered per project, so agents can say "create a task on R1".
- Evaluate whether keys can be the primary keys, instead of separate integer ids.

## 2. Users and jobs

- **The owner:** "What's in the next release, and how far along is it?" "What's not scheduled yet?" "Move this into R-2."
- **A project manager** (such as ada, §4.7; **[A]** only if ada is a lead of a team attached to the project): create releases and milestones, plan work into them, roll over what didn't make it.
- **Any agent:** create a task straight into a release, plan its own task, refer to things by a short key in chat and the CLI.

## 3. Goals, non-goals and success

**Goals:**
- Every project, release, milestone, task and bug has a short, stable, human key that works in the UI, chat and the CLI.
- The owner sees a project's backlog and each release's progress in **two clicks** from Home (AC-PL6-6).
- Planning a task costs an agent **one CLI call**.

**Non-goals:**
- Gantt charts, dependencies between releases, a timeline view.
- Sprints and capacity planning. Speed figures (throughput, cycle time, forecast) live in `project-insights-v1.md`, not here.
- Due-date alarms. A target is a plan, not a deadline.
- Releases across several projects (v1).
- Requests (`REQ-n`) in releases. They're org-wide asks, not project work.

**Success**, measured 30 days after release:
- At least 80% of open tasks in active projects sit in a release or milestone, or deliberately in the backlog with a rank set explicitly (moved at least once). "Active project" is to be supplied by ada. Not a blocker.
- Every ref error names the fix (AC-PL7-2).
- The owner's "what's in the release?" chat questions to ada fall by half. The baseline count (from chat history) is to be supplied by ada. Not a blocker.

## 4. The experience

### 4.0 The model [O]

- A **project** has a **backlog** and **releases**. The backlog is a view, not a container (§4.6). **Releases** have **milestones**.
- A task or bug belongs to one of three places: (a) the project only, which means it's in the backlog; (b) the project and a release; (c) the project, a release and one of that release's milestones (§4.5).
- A release can be created on a brand-new project with no tasks. Tasks are then planned into it.
- A planned task is part of its release before it's delivered. The release's progress counts it as not done until it's Done (§4.3).

### 4.1 Keys [O]

| Key | Example | Numbered | Scope |
| --- | --- | --- | --- |
| Project | `P-2` | by HQ | per org |
| Release | `R-1` | by HQ | per project |
| Milestone | `M-3` | by HQ | per project |
| Task | `T-12` | by HQ (today) | per project |
| Bug | `B-4` | by HQ (today) | per project |

- **P-n is numbered per org on purpose.** Projects are org-level, so one counter serves the whole org. R-n, M-n, T-n and B-n are numbered per project.
- **Display keeps the hyphen:** `T-12`, `R-1`. The CLI, chat links and search accept `T12`, `t12` and `T-12` alike (see §4.1a).
- **The owner wrote `P1` and `R1`.** The app displays `P-1` and `R-1` for readability, and accepts both forms.
- Project P-2 restarts its own R-1, M-1 and T-1.
- **Projects keep their text key** (`chk`) as well as the number. The text key stays the readable qualifier: `chk-T-12`. `P-2-T-12` is accepted too (§4.1a). The UI shows "P-2 · Checkout", with `chk` in the project page header.
- **Numbers are never reused.** A cancelled or deleted T-7 keeps its number, and no other item ever gets T-7. **[F]** A deleted task is a tombstone, and the design already says "deleted items included" (§1).
- **Releases and milestones can't be deleted.** Cancel them instead. Their numbers are never reused either.
- **A moved task gets a new number** in its new project, and keeps everything else. Its old ref redirects to it. **[A]** Moving a task between projects is not confirmed built, and is not part of this PRD. This rule, and AC-PL1-4, apply once a cross-project move exists. **[F]** This reverses the design's fixed-number-scope stance (`docs/design/tasks-projects-docs.md:430`). Rowan to confirm.

### 4.1a Ref parsing [O]

Product rule. Rowan owns the parser; this is the behaviour.
- **Refs are case-insensitive everywhere.** `CHK-T-12`, `chk-t-12` and `chk-T-12` are the same ref.
- **The item part** accepts `T12`, `t12` and `T-12`, for every kind (P, R, M, T, B). A hyphen-less project number follows the next rule.
- **Qualified refs:** the project part is the project's text key (`chk-T-12`, `chk-T12`) or its number (`P-2-T-12`, or `P2-T-12` under the next rule). Qualified refs always work, wherever you are.
- **A hyphen-less `P2` follows one rule, standalone or as a qualifier.** It means the project keyed `p2` if one exists, otherwise project number P-2. Only a legacy key can match, since new keys of that shape are refused. `P-2`, with the hyphen, always means the number. So `P2-T-12`, `projects show P2` and `--project P2` all name `p2` when it exists, and P-2 otherwise.
- **Precedence for a hyphen-less P ref:** a legacy project key first, then a project number, then a short id. The short-id step applies only where a task or bug is accepted. `projects show P12345` never falls back to a short id.
- **New project keys** that are a letter P, R, M, T or B followed only by digits (such as `p2` or `t12`) are refused at creation, with a clear message naming the rule. Existing keys of that shape keep working.
- **Unqualified refs** (`R-1`, `M-3`, `T-12`, `B-4`) resolve in this order: the project named by `--project`; else the project of the agent's current task (`member_status.current_task_id`, origin/v1 `crates/org-office/src/office/tests/work/current.rs`); else the agent's only project, if it is on exactly one. An agent is on a project when it is a member of a team attached to the project, or its project manager (§4.7; the project's Team tab lists the assigned teams, then their members: `information-architecture-v2.md` D37, `ia-v2-stories.md` AC-IA17-2). Otherwise the command errors: "Which project? Use chk-R-1 or --project chk."
- **The owner's CLI calls** have no agent and no current task. An unqualified ref resolves in the `--project` project, else the org's only project. With several projects and no `--project`, it is refused with the fix: "Which project? Add --project <key>, or use chk-R-1." (AC-PL1-9).
- **Unqualified refs in the UI.** On a project page, or any of its tabs, `T12` resolves in that project. In global search, an unqualified ref lists each project's match ("chk-T-12", "pay-T-12"), ordered by project key, then item key. In chat, a ref becomes a link in the thread's project, if the thread has one; otherwise only qualified refs become links.
- **Short ids.** **[F]** A 6-character short id is any 6 lowercase letters or digits (`refs.rs:25-26, 52-58`), so `t12345` reads both as T-12345 and as a short id. A ref that reads as a kind letter plus digits resolves as a number first. If no numbered item matches, it is tried as a short id. Every command echoes the item it resolved, for example "T-12345 · Fix checkout".
- **Short ids name tasks and bugs only.** A release or milestone that HQ hasn't numbered yet shows "Pending" until it is numbered (phase 2, §6.11).
- **[F] Today's parser** is case-sensitive. It knows only the kind letters `T` and `B` (`crates/org-work/src/refs.rs:64-70`), and a project key must be lowercase (`refs.rs:80-87`). `resolve_item` already refuses a short id that matches more than one item, as "the short id is ambiguous" (`refs.rs:132-139`). Case-insensitivity and the kind letters P, R and M are new behaviour.

### 4.2 Keys vs primary keys (for the owner)

You asked whether the keys could simply be the primary keys. My recommendation is **no**: keep a hidden internal id as each item's identity, and make the key a unique label on it. Rowan decides the storage, including whether that internal id is an integer or the ULID used today (a long unique id that sorts by creation time, which the system already gives every record).

Why, in plain terms:
1. **Items exist before they have a key: Pending, then numbered.** A satellite office can create a task while offline. Only HQ hands out numbers, so for a while the task is "Pending". It still needs an identity, comments and links during that time.
2. **A key can change; identity mustn't.** Move T-12 from Checkout to Payments and it becomes `pay-T-4`. If the key were the identity, every comment, link, timeline entry and follow would have to be rewritten, and some would be missed. With a separate identity, nothing moves except the label, and the old ref redirects.
3. **The item tables and the event log are keyed by identity** today (`store/work.rs:18-39`). Changing that would touch every office.
4. **A unique label that is never reused is enough** for people and agents. What they need is that `T-12` always means the same thing.

Reasons 1 and 2 rest on features not built yet (phase 2 satellites, cross-project moves). They are why the choice matters now: changing identity later would touch every office.

Integers aren't needed for fast lookups either. **[F]** Lookup by number isn't built in the office store yet (`crates/org-work/src/ports.rs:183`, `crates/org-work/src/testkit.rs:346`). Lookup by key scans without an index (`crates/org-office/src/store/org/work_view.rs:97-104`). Speed comes from an index on the key, not from the type of id. The existing ULID can stay the identity. Rowan decides (§6.3-6.4).

So: stable identity underneath, unique and never-reused human keys on top.

### 4.3 Releases [O]

- **Fields:** name, optional target date, optional description, status.
- **Statuses:** Planned, In progress, Released (the time is recorded), Cancelled. The transitions are in §4.3a.
- **Target date** shows as "Target 28 Nov". Once passed it reads "Target passed", in neutral grey. It's never amber or red, and never an Inbox item. Amber means only "waiting on the owner".
- **Releasing with open items** asks one question: move them to another release, or to the backlog. The choice is recorded on the release and in each item's timeline.
- **Cancelling** asks the same question for its open items, and records it the same way. Done items stay attached to the cancelled release, as history. Its open milestones are cancelled with it.
- **The roll-over is part of the release action.** Moving the open items, on releasing or cancelling, needs no per-item rights. Each move is recorded as made by the person releasing or cancelling. A started open item rolled into a Planned release starts it (§4.3a).
- **Closed subtasks (Done or Cancelled) of an open parent** follow the parent's plan, and move with it. An open subtask under a Done parent can't happen: Done requires no open subtasks (`tasks-v1` §4.2, Done's guards). `--anyway` overrides only unticked required steps. So at roll-over, subtasks follow their parent's plan.
- **Choosing the release.** The UI offers a picker of the project's other Planned and In progress releases, sorted by target date (no date last), then by number. The earliest is preselected. The CLI's `--open-items next` takes that same default. If there is none, the picker shows "No other open release" with a "Create release" action, and the CLI refuses: "No other open release. Use --open-items backlog, or create one first."
- Items moved from a milestone land in the chosen release **without a milestone**.
- **Roll-over to the backlog lands at the top, in release-page order:** the milestone sections in release-page order (§4.9), each with its items by key number (tasks before bugs on a tie), then the directly planned items by key number (§4.6, AC-PL5-4). Only open milestones carry open items in practice, but the rule is the same for all. The first item of that order ends up highest.
- **Closing with `--open-items`.** `releases release` and `releases cancel` with open items and no `--open-items` are refused, naming the flag (AC-PL2-19). `--open-items R-n` naming a Released or Cancelled release is refused with the planning message: "R-2 is Released: reopen it or pick another release". `--open-items R-1`, naming the release being closed, is refused: "R-1 is the release you are closing. Pick another release, next or backlog."
- **Progress** is done / total items, or points when every counted item (Cancelled excluded) has them. Until points ship (`tasks-v1` AC-TK9-3), progress shows item counts. It shows on the release and on each milestone. A release's progress includes the items in its milestones as well as its directly planned items. It counts top-level items only (not subtasks, §4.5). Cancelled items don't count. With nothing counted (0 / 0) it shows "—" with "Nothing planned yet", as `project-insights-v1.md` AC-IN2-7 (AC-PL2-21).
- **Deleted items** (`work.delete` tombstones, §1) are excluded everywhere, like Cancelled items: from progress, the release page, the backlog, every list and every count of open items. Only their numbers stay reserved (§4.1).
- A release can be edited until Released or Cancelled; after that it's read-only, except its description. `releases edit` of its name or target is refused: "R-1 is Released: reopen it to change its name or target." Reopening makes it editable again.
- **A Released or Cancelled release locks its milestones.** Reopening one of its milestones, moving one of them to another release, creating a milestone on it, editing a milestone's name or target, and planning into it or any of its milestones are refused. A milestone's description can still be edited, and so can the release's own description, Cancelled included. The first four say "R-1 is Released: reopen it first" (or "R-1 is Cancelled: reopen it first"). Planning says "R-1 is Released: reopen it or pick another release" (or "R-1 is Cancelled: reopen it or pick another release"). This check comes before the milestone's own status check. Reopening the release is the only way back (§4.3a). Moving a milestone between two closed releases checks the source release first, so the refusal is the source's ("R-1 is Released: reopen it first"), not the target's (AC-PL3-11 before AC-PL3-7). `tasks new --release R-1` (or `--milestone`) is refused the same way as planning while R-1 is Released or Cancelled (AC-PL4-2).

| Milestone | Reopen by hand, while its release is Released or Cancelled | Refused: "R-1 is Released: reopen it first" (or "R-1 is Cancelled: reopen it first"). Nothing changes. |
| Milestone | Move to another release, while its release is Released or Cancelled | Refused: "R-1 is Released: reopen it first" (or "is Cancelled"). Nothing moves. |
| Milestone | Edit name or target, while its release is Released or Cancelled | Refused: "R-1 is Released: reopen it first" (or "is Cancelled"). Its description can still be edited. |
| Milestone | Create on a release that is Released or Cancelled | Refused: "R-1 is Released: reopen it first" (or "is Cancelled"). No milestone is created. |
| Task or bug | Plan into a closed release, or into a milestone whose release is Released or Cancelled | Refused: "R-1 is Released: reopen it or pick another release" (or "is Cancelled"). The item keeps its plan. |
| Task or bug | Done or Cancelled → reopened, while its release is Released or Cancelled | A system move to the top of the backlog (§4.6). The person reopening needs no plan rights. Recorded: "Moved to the backlog: reopened after R-1 shipped" (or "after R-1 was cancelled"). |
| Task or bug | Done or Cancelled → reopened, while it is in the backlog (never planned, or its release returned it) | An ordinary reopen. It goes to the top of the backlog, like any return (§4.6). |
| Task or bug | Done or Cancelled → reopened, while its milestone is Done or Cancelled and its release is open | A system move: it stays on the release, without the milestone. The person reopening needs no plan rights. Recorded: "Moved from M-2 to R-1: reopened after M-2 was done" (or "was cancelled"). |

**"Started"** means an open item (In progress, Blocked or In review) that has a Started event (`tasks-v1` T8). Done and Cancelled items never start a release, even with a Started event. A subtask's start counts, because the subtask is planned through its parent: its parent's release starts when the subtask starts. Planning an already-started item onto a Planned release, or one of its milestones, starts that release. An item that was started and is back in To do doesn't count. A parent in To do with a started open subtask counts as started, when the parent is planned, moved or rolled over. An item that goes To do to Done directly records Started and Done at the same moment (`tasks-v1` §4.2, AC-TK4-8), but was never open while started, so it never starts a release (Done and Cancelled items never start a release). **Roll-over:** rolling a started open item (In progress, Blocked or In review) into a Planned release starts that release. The start is recorded as made by the person releasing or cancelling.

**An In progress release never returns to Planned.** Once In progress, it stays In progress, even if every started item on it is unplanned or moved away. Only releasing or cancelling takes it out of In progress. Reopening a release that was cancelled while Planned still returns it to Planned (the table above). **Reopening a Released release always goes to In progress**, even if it was released while Planned, unlike a Cancelled release, which returns to the status it had before.

**Bugs** map to these statuses as `project-insights-v1.md` §4.2 does: New and Triaged count as To do; In progress counts as In progress, and its first move there is its Started event; Fixed is Done (its Done time is its last Fixed), and Closed · Verified after Fixed stays Done; Closed as Duplicate, Won't fix or Can't reproduce counts as Cancelled, even if it was Fixed first. A reopened bug is reopened like a task (the table above). So a Fixed bug is not an open item: it counts as done in progress and doesn't roll over.

Every transition is recorded with actor and server time. A system move records the person who reopened the item as its actor. A roll-over move, or a move when a milestone is closed by hand, records the person who closed the release or milestone. Releases and milestones are never deleted.

### 4.4 Milestones [O]

- **Fields:** name, optional target date (same display rules), optional description, status Open, Done or Cancelled.
- A milestone's target can be later than its release's target. That's allowed, with no warning.
- A milestone belongs to **exactly one release**. Moving it to another release moves its items with it, and each item's timeline records it. Only release planners can move a milestone. **Only an open milestone can move:** a Done or Cancelled milestone stays on its release ("M-2 is Done: reopen it, then move it"). Moving it into a Released or Cancelled release is refused. Moving it out of one is refused too (§4.3). Moving a milestone that holds started items into a Planned release starts that release (§4.3a, same rule as AC-PL2-7).
- **A Released or Cancelled release** refuses new milestones, reopening its milestones, moving them, and editing their name or target: "R-1 is Released: reopen it first". Only a milestone's description stays editable. Planning into them is refused too: "R-1 is Released: reopen it or pick another release" (§4.3, §4.3a).
- **Done** is set by a release planner, or with its release (§4.3a). Closing by hand with open items warns and names them. If confirmed, the open items stay planned on the release, without the milestone. Each item's timeline reads "Moved from M-2 to R-1: M-2 done". In the CLI, `milestones close M-2` with open items is refused unless `--confirm` is given: "M-2 has 3 open items: T-4, T-7, T-9. Add --confirm to close it. They stay planned on R-1, without the milestone." (AC-PL3-18). The items named in that message are listed by key number, tasks before bugs on a tie.
- **Planning into a Done or Cancelled milestone is refused.** A release planner can reopen a Done or Cancelled milestone while its release is open. Reopening a release reopens the milestones that closed with it (§4.3a).
- **Cancelling a milestone by hand** keeps its open items planned on the release, without a milestone. **Decision.** With open items it warns like close and needs `--confirm` in the CLI: "M-2 has 3 open items: T-4, T-7, T-9. Add --confirm to cancel it. They stay planned on R-1, without the milestone." (AC-PL3-19).

### 4.5 Planning a task [O]

- A task or bug sits in **at most one** of: a release, or a milestone (which implies its release). Planning it somewhere new replaces the old place.
- **Subtasks** (`tasks-v1` T7) follow their parent's plan. This is a new rule, set here. Planning a subtask on its own is refused, with a message naming the parent: "T-12 is a subtask: plan the parent, T-9".
- A subtask created under a planned parent, or promoted from a step of one, takes the parent's plan, and follows every later change to it. Like any subtask, it has no rank. "Promoted" in this PRD means only step → subtask. Creating a subtask with its own plan (`tasks new --parent T-9 --release R-1`) is refused: "Subtasks follow their parent's plan."
- **Done and Cancelled items can't be planned or unplanned by hand.** They keep their plan as history. Reopening follows §4.3a.
- Subtasks show **under their parent** in the Backlog and on the release page, not as rows of their own. Under a parent they sort by key number, tasks before bugs on a tie.
- Unplanning (moving to the backlog) follows the same permission rule as planning (§4.7).
- Every move is a timeline entry: "Planned into R-1 by Kai", "Moved from M-2 to the backlog by ada".

### 4.6 The backlog [O]

- **Definition:** the project's tasks and bugs with no release and no milestone. It's computed, never stored.
- Open items only by default (not Done or Cancelled). A "Show closed" filter adds the rest. Closed items have no rank: they sort by close time, newest first, below the open items.
- **Order:** a rank. New items land at the bottom. Returns land at the top, unless `--rank bottom` is given (AC-PL5-10). A return is an item that comes back to the backlog (its release closed, unplanned, or reopened after its release closed). **`tasks plan T-12 --backlog` on an item already in the backlog is a no-op:** it is idempotent and the rank doesn't change, unless `--rank` is given (AC-PL5-11). Separate returns go in arrival order: the latest arrival first. **A batch that arrives together keeps its own order at the top:** a roll-over batch keeps release-page order (milestone sections in §4.9 order, each with its items by key number, tasks before bugs on a tie, then direct items by key number, §4.3, §4.9). Several refs moved with `--rank top`, or with `--backlog` alone, keep the order given. The first of the batch is the highest (AC-PL5-4). With `--backlog --rank top` over a mix of planned items and items already in the backlog, every ref moves to the top in the order given (AC-PL5-10). With bare `--backlog` over such a mix, only the planned refs move to the top, in the order given; the refs already in the backlog keep their rank (a no-op for them, AC-PL5-11). **Reopening a closed item that is already in the backlog** (never planned, or its release returned it) puts it at the top too, like any return. Closed items have no rank, so it takes a new one on reopen.
- **Re-ranking** (`--rank top|bottom|up|down`, or `--before <ref>` / `--after <ref>`, in the CLI; several refs move as a block, and the block order depends on the verb: `top`, `bottom`, `--before` and `--after` place the refs in the order given, while `up` and `down` keep their current relative order and shift each by one, as the UI does (AC-PL5-8, AC-PL5-12); row-menu moves in the UI, drag later): release planners can re-rank any backlog item. **The UI has no `--before` or `--after`.** It reaches those placements with repeated Move up and Move down until drag ships (PL-8). Other members can re-rank only their own items (assigned to or created by them).
- **Re-ranking in the UI (v1.0):** each Backlog row's menu has Move to top, Move up, Move down and Move to bottom. They work from the keyboard too (Eden designs the keys). In multi-select they move the selection as a block: the rows keep their relative order. They show under the re-rank rights above: a member sees them only on items they may re-rank, and only those items can join a re-rank selection. Subtasks have no rank, so no moves. Drag stays Next (PL-8).
- **Several refs are all or nothing.** If any ref in one command is refused, nothing moves, and the error lists each refused ref with its fix, in the order the refs were given. The UI's multi-select actions follow the same rule: they already disable ineligible rows, so a selection can't include a refused item (AC-PL5-8, AC-PL5-7).
- **Only backlog items have a rank.** `--rank` on a planned item is refused. Subtasks carry no rank; they show under their parent.

### 4.7 Who can plan [O]

- **Project manager** means the owner, or a lead of a team attached to the project. **[F]** A team's lead is `Team.lead_member_id`, and "also leads its projects" (`crates/org-proto/src/org.rs:124-126`). **Decision.** This PRD says "project manager", not "manager", so it never clashes with `tasks-v1`'s "the assignee's manager".
- **Release planners** are the owner, project managers, and members the owner allows. The owner allows a member from the project's Team tab ("Can plan releases"), or with `org-agent projects planners add|remove|list <member> [--project <key>]`. `add` and `remove` are owner only; anyone else is refused ("Only the owner can change who can plan releases."). `list` shows who can plan, sorted by name, and any member of the project can run it. Both routes give the same grant, and each change is recorded with actor and server time. Eden designs the control.
- **Release planners can do everything with releases and milestones, except reopening a Released or Cancelled release:** create, edit, start by hand, release and cancel releases; plan or unplan any task or bug; re-rank any backlog item; create, edit, close, cancel, reopen and move milestones.
- **Reopen a Released or Cancelled release:** the owner or a project manager only.
- **Other members** plan and unplan only their own tasks and bugs, into an existing release or milestone, and re-rank only their own backlog items (§4.6). Own items are those assigned to or created by them.
- **The roll-over** on releasing or cancelling (§4.3) is part of the release action. It needs no per-item rights, and each move is recorded as made by the person releasing or cancelling.
- **System moves** on reopen (§4.3a) need no plan rights.
- Engineering decides the permission mechanics.

### 4.8 Features (dependent on the features phase) [O]

Features (`FEAT-n`) stay the doc-backed "what"; releases and milestones are the "when". A feature can be targeted to a release, and the release page lists its features. This waits for phase 3 (design:138-139).

## 6. Requirements for engineering (Rowan designs the how)

1. A project number `P-n`, org-wide, assigned by HQ, alongside the existing text key.
2. Release and milestone records, numbered per project by HQ, with the fields and statuses in §4.3-4.4.
3. Keys are unique per (project, kind, number), enforced by storage, and never reused, deleted items included. The designed unique index (design:430) isn't built yet. This is §6.3, and a dependency of PL-1.
4. Identity stays separate from the key (§4.2). Rowan picks integer or ULID.
5. Ref parsing follows §4.1a for every kind: case-insensitive; `T12`, `t12`, `T-12`, `chk-T12`, `chk-T-12` and `P-2-T-12`; hyphen-less `P2`, standalone or as a qualifier, as the project keyed `p2` if one exists, otherwise P-2; new keys of shape P, R, M, T or B plus digits refused at creation; unqualified refs resolved by `--project`, current task (`member_status.current_task_id`), then only project; numbers before short ids, with the resolved item echoed; a hyphen-less P ref as a legacy project key, then a project number, then a short id (the short id only where a task or bug is accepted); short ids for tasks and bugs only. In the UI: unqualified refs resolve in the project page's project, global search lists each project's match, and chat links resolve in the thread's project, or only qualified refs link.
6. A moved task gets a new number; its old ref redirects (UI, CLI and search). Dependent on a cross-project move existing (§4.1).
7. A task or bug holds at most one plan link: release or milestone. Subtasks carry their parent's plan, closed subtasks (Done or Cancelled) of an open parent included (§4.5, §4.3). A subtask can't be created or planned with its own plan. Done and Cancelled items can't be planned or unplanned by hand (§4.5).
8. A backlog read: unplanned, open by default, ranked, subtasks under their parent. With closed items shown, they follow by close time, newest first. Not stored as a list.
9. A rank on top-level backlog tasks and bugs, with top, bottom, up one place, down one place, and before or after a named item (also as a block for several items; the CLI takes several refs) and, later, drag-reorder. Reopening a closed backlog item gives it a rank at the top. New items land at the bottom. Returns land at the top, unless `--rank bottom` is given (AC-PL5-10): separate returns latest first, a batch in its own order (§4.6). Block order per verb: top, bottom, before and after keep the order given; up and down keep the current relative order (AC-PL5-8). Commands with several refs are all or nothing. Re-ranking follows §4.6. `--rank` on a planned item is refused; subtasks carry no rank.
10. Every plan change, release status change, milestone move and close is recorded with actor and server time. Roll-over moves, and moves when a milestone is closed by hand, record the person who closed the release or milestone.
11. **(Phase 2.)** Satellite numbering: releases and milestones created on a satellite show "Pending" until HQ numbers them, as tasks do. A Pending release or milestone can't be named from the CLI until it is numbered. Agents use it after numbering.
12. The CLI in §5.
13. **Backfill.** Existing projects get `P-n` in creation order (unknown dates last, then by name). Existing open top-level items get a backlog rank by creation time, oldest at the top, tasks and bugs interleaved by creation time.
14. The transitions in §4.3a, including the automatic ones, the roll-over, the moves when a milestone is closed by hand, and the system moves on reopen. A release reopen must tell the milestones that closed with it from those closed by hand before. A reopened Cancelled release returns to the status it had before cancelling; a reopened Released release keeps its release date in its history only. A Released or Cancelled release refuses reopening, moving or creating its milestones ("R-1 is Released: reopen it first") and planning into it or them ("R-1 is Released: reopen it or pick another release"), checked before the milestone's own status. Moving a milestone that holds started items into a Planned release starts it ("started" per §4.3a: a Started event, not To do now, subtask starts included). Planning an already-started item onto a Planned release starts it. Only open items count as started: Done and Cancelled items never start a release. A Blocked item counts only if it has been started (has a Started event); one blocked straight from To do, never started, doesn't. Only open milestones move; a milestone move checks the source release first, then the target's. Releases and milestones have no delete. A Released or Cancelled release also refuses editing a milestone's name or target; only its description stays editable.
15. The permissions in §4.7, including the "Can plan releases" grant (the Team tab, and `projects planners add|remove|list` in the CLI; add and remove owner only).
16. Progress counts top-level items only, excluding Cancelled.
17. The UI entry points in §4.9 need plan and multi-item plan operations, and per-member rights the UI can read, so each action shows only to members allowed to use it.

With several refs the block moves as a unit. The command is all or nothing: if any ref is refused, nothing moves, and the error lists each refused ref with its fix, in the order the refs were given. ## 9. Open questions and dependencies

- **Ref collisions:** decided (§4.1a, AC-PL1-6 to AC-PL1-10, AC-PL1-12). Rowan implements the parser.
- **[A] Moving tasks between projects** is not confirmed built and is not part of this PRD. AC-PL1-4 applies when it exists. Its new number reverses the design's fixed number scope (design:430): Rowan to confirm.
- **[F] Deleting items** is known: `work.delete` leaves a tombstone (`crates/org-proto/src/work.rs:430`), and numbers are never reused, "deleted items included" (`docs/design/tasks-projects-docs.md:298`). AC-PL1-3 tests it.
- **Decided:** "project manager" is the owner, or a lead of a team attached to the project (§4.7).
- **Decided:** a Done or Cancelled task reopened while its release is Released or Cancelled moves to the top of the backlog; reopened while its milestone is Done or Cancelled and its release open, it stays on the release without the milestone. Both are system moves, and the timeline records why (§4.3a, AC-PL2-10, AC-PL2-13).
- **Decided:** a hyphen-less `P2` names the project keyed `p2` if one exists, otherwise P-2 (§4.1a, AC-PL1-6, AC-PL1-12).
- **Decided:** backlog rank and re-rank rights (§4.6, AC-PL5-4, AC-PL5-5). Re-ranking in the UI in v1.0 by row menu and keyboard, single or block; drag stays Next (§4.6, AC-PL5-7).
- **Decided:** release planners can do everything with releases and milestones; only the owner or a project manager reopens a Released or Cancelled release; the roll-over needs no per-item rights (§4.7, AC-PL2-16).
- **Decided:** closing a milestone as Done by hand leaves its open items on the release, without the milestone (§4.4, AC-PL3-9).
- **Decided:** unqualified refs in the UI resolve in the page's project, list each project's match in global search, and link in chat only where the thread has a project (§4.1a, AC-PL1-14).
- **Decided:** a Released or Cancelled release refuses reopening, moving or creating its milestones, and planning into them: "R-1 is Released: reopen it first"; planning into it or them says "R-1 is Released: reopen it or pick another release" (§4.3, §4.3a, AC-PL3-10 to AC-PL3-13, AC-PL4-2).
- **Decided:** the UI's "New task" form has an optional "Plan" field (§4.9, AC-PL6-13). Reopening a release asks for the reason in a dialog, and Edit on a Released release changes the description only (§4.9, AC-PL6-9).
- **Decided:** the v1.0 UI entry points: "Plan ▾" on every task and bug, multi-select, release header and milestone section actions, each shown only to members allowed to use it (§4.9, AC-PL6-7 to AC-PL6-12).
- **Decided:** the backfill ranks existing open top-level items by creation time, oldest at the top (§6.13, AC-PL1-11).
- **Decided (Rev 9):** closing a milestone with open items needs `--confirm` (AC-PL3-18). Commands with several refs are all or nothing (§4.6, AC-PL5-8). A batch landing at the top of the backlog keeps release-page order (roll-over) or the order given (§4.3, §4.6, AC-PL5-4). `releases release|cancel` with open items needs `--open-items` (AC-PL2-19). The owner's CLI refs resolve by `--project`, then the only project (§4.1a, AC-PL1-9).
