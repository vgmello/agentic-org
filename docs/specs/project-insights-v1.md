## 3. Goals, non-goals and success

**Goals:**
- Every progress and speed figure is **derived from recorded events**. Nothing is typed.
- The owner sees each open release's progress and each open milestone's in **two clicks** from Home: Home → project → Insights. A release's own page is a further click.
- Every number opens the items behind it.

**Non-goals:**
- per-agent leaderboards or rankings;
- estimates or hours entered by hand;
- Gantt charts, timelines or dependencies (as in projects-planning-v1 §3 non-goals);
- alarms or health rules driven by target dates;
- org-wide progress across projects (Insights v1 is per project);
- points charts before points ship: charts show item counts until then (tasks-v1 AC-TK9-3, §7).

**Success**, 30 days after Insights v1 ships:
- The owner's "how far along is R-n?" chat questions to agents fall by half. **[A]** Baseline from chat history (ada).
- 100% of figures on the tab trace to items: a test opens each one and checks its list. A count's list has that many items. A percentile's or median's list is its whole population, as many items as the "n items" shown. A time figure's items have clipped intervals that sum to it.

- **One basis for all durations (shared rule).** Cycle time (first Started → last Done), lead time (created → last Done), time in status and "over its usual time" (§4.4) all exclude spans spent in Done or Cancelled. Example: started day 0, Done day 2, reopened day 9, Done day 10 gives a cycle time of 3 days, not 10.
- **Durations are computed in whole seconds** (integer arithmetic) and then formatted. Percentiles and medians are taken over those whole-second values.
- **One duration formatter** serves every aggregate duration metric: Insights, the Flow tile, the CLI report and the away digest's median cycle time (away-digest-and-timezones-v1 AW-9, AC-AW9-1). The away digest's elapsed spans (window length, "blocked 1 h 40 min") use that PRD's own exact format (away-digest-and-timezones-v1 §4.3), not this one. Under 1 h: whole minutes ("45 min"). Under 48 h: whole hours ("26 h"). 48 h and more: days with one decimal ("2.6 d"), where days = floor(seconds × 10 / 86400) / 10, in integer arithmetic. Always rounded down. Time in progress uses it too, with the exact hours in the tooltip.
- **"Items left"** = open items in scope (total − done, Cancelled and deleted items excluded). It is always counted in items, even when the % uses points.
- **Flow figures count top-level tasks and bugs only.** Throughput, cycle time, lead time, time in status and time in progress never count subtasks.
- **When a bug is "Done".** Everywhere in this PRD, a bug is Done when it reaches Fixed, and its Done time is its last Fixed. A later Closed · Verified doesn't change it (verification only follows Fixed, work-items-ux FIX-5). A bug closed as Duplicate, Won't fix or Can't reproduce, including one Fixed first, counts like Cancelled: it leaves scope and is never Done. A reopened bug is open again until it reaches Fixed. The away digest uses the same rule (away-digest-and-timezones-v1 §4.3, Bug delivery rule).
- **Bug status mapping (time in status).** New and Triaged count as To do. In progress counts as In progress. "Started" for a bug is its first move to In progress. Time after Fixed or Closed counts as Done, so it is excluded. Bugs have no Blocked or In review status (`crates/org-proto/src/work.rs` at origin/v1, `ItemStatus`: a bug is new, triaged, in_progress, fixed or closed), so bugs never appear in those buckets.
- **Population.** Throughput, cycle time and lead time count the items whose last Done falls in the period; for a release period, the Done top-level items currently planned on the release or its milestones, with the release span (§4.2 Throughput) as the period. **Cancelled items are never counted** in throughput, cycle time or lead time. Only items that are Done now count: an item reopened and not yet Done again doesn't count, even if its earlier Done fell in the period. For a release period, the population counts the items whose Done time falls within the release span (created → now, or → Released or Cancelled). **For a release period, the release span clips time in status and time in progress only**: their intervals are clipped to it. **Cycle time and lead time are never clipped.** They use the item's full history, and the span decides only which items count (Done within the span). An item created 3 weeks before the release and done inside its span has a lead time from its creation. **Items reopened after the release and moved to the backlog drop out of that release's throughput, while its frozen burn-up keeps them.** This is intended: throughput counts what is planned on the release now, and the burn-up is a frozen record (AC-IN4-4).
- **Time in status population (IN-10).** Every status interval that overlaps the period, clipped to the period, open items included. **Cancelled items are excluded.** A release period limits the population to the release's items: the top-level tasks and bugs currently planned on the release or its milestones. **The period is then the release span** (creation → now, or → Released or Cancelled): time before the release existed doesn't count, even for an item that sat in To do long before it was planned in.
- **Percentiles** (median, 85th) use the nearest-rank method. Each shows its population as "n items". With fewer than 5 items, a percentile shows "—, n items" (for example "—, 3 items"), never a number.
- **Points rule, per chart.** A chart uses points only when every item in its current scope has points. For throughput, the scope is the done items in the period. Then the chart's whole history is recomputed in points, using each item's current points, so the scope and done lines stay comparable. Items that were in scope on past days but left it without points count as 0 in that history. Otherwise the chart shows items throughout. Each chart decides on its own.
- **Filters:** period (7, 30 or 90 days, or a release), team, member. The filter is in the URL. **Defaults when the URL has no filters:** period 30 days, all teams, all members. Choosing "Release" in the period filter opens a picker: open releases first, then closed ones under "Closed". The current release (§4.1) is preselected (or, with no open release, the most recently closed one, AC-IN2-8). The URL carries `?period=release:R-n`. When the project has no releases, the option is disabled with "No releases yet".
  - **Progress figures ignore all three filters:** completion %, release rows, burn-up, milestone rows and the project header. The UI says "Progress isn't filtered". The burn-up's release switcher isn't a filter.
  - **Flow figures use them:** throughput, cycle time, lead time, time in status and time in progress. The period filter affects only these. The team and member filters affect only these.
  - For time in status, the member filter attributes each interval to whoever was the assignee during it.
  - For time in status, the team filter counts each interval for the team its assignee was on during that interval. Unassigned intervals count for no team.
- **Attribution.** An item counts for the member who was its assignee when it went Done. Unassigned items count only at project level. The owner's work counts under the owner. The team filter counts items whose assignee at Done was on the team at that time.
- **Per-member figures** (done, cycle time) appear only when a member is filtered, for coaching. There's no table or chart that ranks members.
- **Every number links** to the items behind it, in the Work list:
  - a count, a bar, a release or milestone row or a scope step opens exactly those items, and the list's count equals the number;
  - a percentile or median opens its whole population, and the list's count equals the "n items" shown;
  - a time figure (summed time in a status, time in progress) opens the items whose clipped intervals sum to it.
- **States, per section:**

### 4.4 "Usual" figures for the away digest

This PRD owns these definitions. `away-digest-and-timezones-v1.md` uses them (its §5 requirement 5 and AC-AW5-4 defer to this PRD) and doesn't define its own.

- **Usual cycle time** = the project's median cycle time over the last 90 days, per kind (task, bug; cycle time is per kind), with at least 10 done items of that kind in the window.
- **Over its usual time.** Applies only to open items. An open item that was never Started is never over its usual time. An item is over its usual time when the time since it was first Started, excluding spans spent Done or Cancelled (the same basis as cycle time), exceeds the project's 85th-percentile cycle time for its kind (same window and minimum).
- **Usual throughput for a span** = the project's median items done per span, counting all kinds together (top-level tasks and bugs), using non-overlapping spans of the same length laid back from now over the last 90 days, all hours counted. Only full spans count: the current span (the one ending now) and a partial oldest span (shorter than the span length) are excluded. No comparison unless at least 2 full spans fit. The minimum of 10 done items counts only the done items in the full spans used.
- **Below a minimum** (10 done items of a kind for cycle time and "over"; 10 done items in the full spans used, or fewer than 2 full spans, for throughput), the digest shows no comparison.
- The same population and Cancelled rules as §4.2 apply. **The fewer-than-5 rule of §4.2 doesn't apply to span medians in usual throughput**: its minimum is the 10 done items in the full spans used.

## 5. Requirements for engineering (Rowan designs the how)

1. Every figure is computed from `WorkEvent`s and plan-change events; none is stored as typed input.
2. **Burn-up history** must reflect scope as it was on each past day, including items planned in, moved out, cancelled, reopened and steps promoted to subtasks (which don't count, as they aren't top-level). Each day's point is the state at the end of that day in the bucketing zone (§5.4); today's is the state now. A Released or Cancelled release's last point is its state at the moment it closed, without the open items moved out then. Rowan chooses derive-on-read or daily snapshots. A milestone moved between releases moves its items' scope and done on that day.
3. One query set serves Insights, the project header's progress, the Overview Flow tile, the project status report (`project-status-ux.md:31`, A40 at :111), the CLI and the away digest, so the numbers have the same totals everywhere. One shared calculation returns the percent display value (§4.2 rounding) for the header, Home and Insights. The shared percent calculation ships in v1.0 (header, Home, releases); Insights, the Flow tile and the digest reuse it in v1.1. The shared duration formatter (§4.2) covers the aggregate duration metrics only; the away digest's elapsed spans keep that PRD's own format.
4. Day and week boundaries: the UI buckets in the viewing account's time zone. The CLI and server-side readers use the zone of the account they act for. Agents have no zone (away-digest-and-timezones-v1 Z1), so for agents this PRD uses the earliest-created owner account's zone (§9 D14). Until TZ-1 ships: the browser's zone in the UI, HQ's zone server-side. Totals are identical for every viewer; only day and week bucket edges may differ.
5. **(Phase 2.)** Satellite-created items count once HQ has them; figures note "Pending items from {office} not counted yet" when any are pending (AC-IN8-3).
6. Every figure's item list is addressable by URL.
7. A reopened Done item leaves the done line on its reopen day (the line can step down, AC-IN4-9).

The tab appears before costs; cost sections join it when costs ship. The project page's tab list (information-architecture-v2 §4, the Work row) is amended.
2. **Labels.** Status time is "Time in progress". "Work time" stays the cost spec's session time (`costs-and-insights-ux.md:40`, :58), which isn't tracked yet; the spec warns that "1 day" must not read as "1 day of work" (:95).
3. **Progress leads.** Insights leads with Progress; cost follows when it ships. The cost spec has Insights lead with the investment (INS-5, `costs-and-insights-ux.md:147`), so INS-5 is amended when costs ship (Eden hand-off, §8).
4. **A Released release's burn-up freezes at the moment of release.** Reopened items moved to the backlog later (projects-planning-v1 §4.3a, AC-PL2-10) don't change it (AC-IN4-4). A reopened release unfreezes and continues; a Cancelled release freezes at the moment of cancelling (AC-IN4-5). The last point is the state at that moment: open items moved out then are excluded, so scope equals done (AC-IN4-7).
5. **A minimal Flow tile, no separate progress strip.** The Flow tile isn't built; it exists only in `project-status-ux.md:46-50`. IN-1 adds a minimal one: done in the last 7 days, median cycle time, the current release % and the current release's open milestones with their %, at most 3, then "+N more", linking to Insights (AC-IN1-2). AC-IA17-2 is amended to match (D40). Eden designs it and reconciles it with the project-status spec and IA v2's Overview (information-architecture-v2 §6, the project page: "goal, status, progress, Needs you, recent activity").
6. **Items, not points, until points ship** (tasks-v1 AC-TK9-3, Next).
7. **Current release** = the earliest In progress release, else the earliest Planned one, in the release picker's order (§4.1, AC-IN1-2).
8. **Time in status and time in progress are in Insights v1** (IN-10). T8 already derives them in v1.0, and they answer the owner's "how many hours". Work time and cost stay Next (IN-11): they need session tracking.
9. **One project progress number.** The project header (IA D15, AC-IA17-1) uses IN-2's definition: top-level tasks and bugs, Cancelled and deleted items excluded, backlog included. D40 records that it amends D15 (AC-IN2-4).
10. **This PRD owns "usual"** for the away digest (§4.4, IN-13).
11. **Cancelled items are excluded** from throughput, cycle time, lead time and time in status (AC-IN5-1, AC-IN6-1, AC-IN10-1).
12. **Points are per chart** (§4.2, AC-IN2-5).
13. **Attribution is the assignee at Done** (§4.2, AC-IN7-4).
14. **Day and week boundaries** use the viewing account's zone in the UI and the acting account's zone server-side. Agents have no zone, so for agents Insights uses the earliest-created owner account's zone. This is this PRD's own decision. Before TZ-1: the browser's zone in the UI, HQ's zone server-side. Totals are identical for every viewer (§5.4, AC-IN7-5).
15. **Insights is the last tab**, after Conversations (§4.1, AC-IN1-1, D40).
16. **Time in status:** exclusive buckets, "Waiting on you" as an overlay, interval-overlap population, In review hidden until TK-5. Per bucket, the median of each item's clipped sum, over items with time in that bucket (§4.2, AC-IN10-1).
17. **Filters:** progress figures ignore them; flow figures use them (§4.2, AC-IN7-1).
18. **Milestones get rows, not a burn-up, in v1.** Milestone burn-up is Next (§4.2, AC-IN3-3).
19. **Release population and span:** Done top-level items currently planned on the release or its milestones; span from creation to today, or to Released or Cancelled (§4.2, AC-IN6-2).
20. **Two clicks from Home:** Home → project → Insights. The release page is a further click (AC-IN1-4).
21. **The Progress section's layout:** the project %, then one row per open release, then the current release's burn-up with a release switcher, then the open milestone rows. The collapsed "Closed" heading below the open release rows holds the closed releases' rows (§4.1, AC-IN2-8). The switcher isn't a flow filter (§4.1, AC-IN2-6).
22. **A day's burn-up point** is the state at the end of that day in the bucketing zone, and now for today. A closed release's last point is its state at the moment it closed (§4.2, AC-IN4-7).
23. **Points history:** items that left a chart's scope without points count as 0; throughput's scope is the done items in the period (§4.2, AC-IN2-5).
24. **Flow figures count top-level tasks and bugs only** (§4.2, AC-IN5-1, AC-IN6-1, AC-IN10-1).
25. **Periods are rolling windows** of 24-hour days ending now. Partial first and last bars are shown and marked "partial". Usual throughput drops the partial oldest span and excludes the current span (§4.2, §4.4, AC-IN5-2, AC-IN13-1).
26. **Drill-down by figure kind:** a count opens its items; a percentile or median opens its whole population ("n items"); a time figure opens the items whose clipped intervals sum to it (§4.2, AC-IN7-3).
27. **"Waiting on you" uses tasks-v1's five cases** (tasks-v1 §4.1, T8), overlapping cases counted once. The cost spec's extra cases (`costs-and-insights-ux.md:140`, TIME-7) join when those sources reach the Inbox; Eden reconciles (§8).
28. **States are per section.** The "after the first item is done" empty state (any task or bug, ever) applies only to throughput, cycle time and lead time in Speed; time in status shows once any item has time in a status (§4.2, AC-IN8-1). The forecast's not-enough-data state belongs to IN-9.
29. **No emoji anywhere;** statuses are an icon plus a word (§4.2, AC-IN8-4).
30. **One basis for all durations.** Cycle time, lead time, time in status and "over its usual time" all exclude spans spent in Done or Cancelled. Stated once in §4.2 (AC-IN6-1, AC-IN10-1).
31. **Usual throughput uses a 90-day lookback and full spans only.** The current span and a partial oldest span are excluded. No comparison below 2 full spans. The 10-item minimum counts only the full spans used (§4.4, AC-IN13-1).
32. **Percent rounding:** whole numbers rounded down; 100% only when everything in scope is done; at least 1% when anything is done. One shared calculation feeds the header, Home and Insights (§4.2, AC-IN2-1, AC-IN2-4).
