## 1. The problem

**[F] The owner, 2026-11-12:**
- "I want to talk cost and token budgets per agent and task and cost budget per task."
- "Agent and task, they are two different things… an agent can work in multiple tasks."
- "The task they aggregate up to the milestones, they aggregate up to the releases, and they aggregate up to the project… overall project engineering cost, or implementation costs."
- "Once the project goes live, we're also going to have to maintain the project as a support basis… support is a V2."
- "Total cost of implementation of the project, and then total cost of support… customer support versus production monitoring versus the implementation… R&D cost… KTLO."
- "The R&D cost we should have on V1, but the KTLO / production support part later for V2. We can scope and make sure that whatever we're building is going to have support for this."

**[O] Why it matters now.** Agents spend real money every turn, and the owner can't see where it goes. Without a per-task number, the owner can't tell a $3 fix from a $60 one, can't cap a task that runs away, and can't say what a release or a project cost to build. Without a work type in the data from day one, the support costs that start when a project goes live would need a migration to separate.

## 2. Users and jobs

- **The owner:** "What did T-12 cost, and who spent it?" "What has R-1 cost so far?" "What has this project cost to build?" "Stop this task if it passes $20." "Never let Kai spend more than $50 a day." "Later: what does it cost to keep this project running?"
- **A project manager** (the owner, or the lead of a team attached to the project; `projects-planning-v1` §4.7): set budgets on their project's tasks and releases, and report cost without computing it, in the app or CLI (never in repo files, requirement 28a).
- **An agent:** know its task's budget and what's left, propose an estimate when it creates a task (v1.1), and stop cleanly when the budget is reached.

## 3. Goals, non-goals and success

**Goals:**
- Every agent session run's tokens and cost are recorded and attributed to a task, or to a "Not on a task" bucket. Nothing is typed.
- The owner sees a task's cost on the task page, and a release's or project's cost in **two clicks** from Home (Home → project → Insights). **v1.0:** a release's cost is two clicks from Home (Home → project → Releases, the release header, §6); "Project cost is CLI-only in v1.0" (`org-agent cost show`, §7). The Insights route applies from v1.1, with CB-9.
- A task budget stops work on that task when reached, and waits on the owner.
- Every cost record carries a work type, so v2 adds Run (KTLO) without migrating v1 data.

**Non-goals (v1):**
- Run work: support, incidents, maintenance, monitoring, and KTLO cost (v2, §10).
- Money for people: hourly rates (v2). v1 shows people's time in progress only.
- Finance treatment: capitalized R&D vs OpEx, invoices, billing reconciliation with providers.
- Org-wide cost Insights beyond totals (v2). v1 has only the minimal org Cost page of CB-13: totals by project and by agent, R&D only.
- Forecasts of cost ("at this pace R-1 costs $X").
- Per-agent leaderboards or rankings (as `project-insights-v1` §3).
- Re-pricing history when prices change.

**Success**, 30 days after release:
- At least 90% of agent cost in active projects is attributed to a task, not "Not on a task". **[A]** "Active project" from ada, as `projects-planning-v1` §3.
- No agent working on a task runs more than one turn over its current limit (AC-CB6-3), after any Allow once. Measured from the budget events.
- The owner's "what did this cost?" chat questions to agents: zero, since every answer is on a page. **[A]** Baseline from chat history (ada).

## 4. Definitions [O]

| Term | Definition |
| --- | --- |
| **Work type** | What kind of work a task or bug is. **Build** (v1: the only choice and the default) or, in v2, a Run type: **Support**, **Incident**, **Maintenance**. A subtask has its parent's work type. |
| **Cost label** | How a work type's cost is reported. Build → **R&D**. Run types → **KTLO** (keep the lights on). Synonyms the owner may know: "change the business" (R&D) vs "run the business" (KTLO); sustaining engineering (KTLO); capitalized R&D vs OpEx (finance treatment is out of scope). |
| **Usage record** | One report of tokens and cost from a runtime, normally one per turn (F2). The smallest thing stored. It has the agent, the time, the runtime, the model, the four token counts, the cost, the cost basis, the price used, the task it was attributed to (or the bucket), how it was attributed (current task, review or invoked for the task, fallback, or none), and that task's work type at that time. |
| **Session run** | An agent's work from wake to sleep (`agent-run-modes-ux.md` RUN-5). A session run has many usage records and may span several tasks. Not the **Run** work type (KTLO, v2): in this PRD the lowercase noun "run" (for example "excludes N runs with no price") always means a session run, and Run with a capital R is always the work type. |
| **Current task** | The task or bug an agent says it is working on (`work.set_current`, F16). Attribution uses the current task **at the time of each usage record**. |
| **Work for a task** | A reviewer reviewing a task, or a helper or other agent invoked for it. Its usage goes to that task, whatever its own current task (C21). |
| **Agent × task** | The base roll-up: the sum of an agent's usage records attributed to one task. |
| **Not on a task** | Usage with no current task, no work-for-a-task context, and no fallback match (§5.1 requirement 2). It goes to the project's bucket when the agent is a member of exactly one project; otherwise to the **org** bucket. Its work type is Build in v1. |
| **Tokens** | Four counts, always shown split on hover or in tables: input, output, cache read, cache write. **Total tokens** = the sum of the four. Token budgets count total tokens. Tokens always count, priced or not. Totals include cache reads, which usually dominate agent usage. **[A]** Example: one typical agent turn reads 150,000 cache-read tokens and writes 3,000 output tokens, so its total is about 155,000 tokens, and 20 turns is about 3 M. Owners size token budgets from totals like this, not from output alone. I assume the figures and will check them against real records. |
| **Cost** | US dollars, stored with the price used at the time. Shown as "$4.12" when the runtime reported it, "≈ $4.12" when the office priced tokens from the price list, "—" when the run has tokens but no price (a **run with no price**, for example a run on a model missing from the price list). A missing cost is never shown as $0. |
| **API-equivalent cost** | The cost of an agent on a subscription plan: what the same tokens cost at API list prices. Labelled "API-equivalent cost" wherever such an agent's cost shows; a total that includes any shows "includes API-equivalent". |
| **Budget** | A limit on a task, an agent (per day, per month) or a release, in US dollars **or** total tokens, never both. A bug can carry a budget under the same rules as a task: "task budget" in this PRD covers tasks and bugs. |
| **Spent** | For a budget, the cost (or total tokens) counted against it, in the budget's unit. A parent task's spent is its total (own plus subtasks). Session runs with no price add nothing to a dollar budget. API-equivalent cost counts against a dollar budget like any other cost. |
| **Spent at release** | A Released release's cost, frozen when it was released. Shown next to its current cost (§4.1). Re-releasing a reopened release replaces it with the new figure. |

**Naming.** **KTLO** means "keep the lights on": the cost of running what is already built (support, incidents, maintenance). **Build** and **Run** are the plain names for the two kinds of work: Build is planning and delivering new things, Run is keeping the live thing healthy. **R&D** is the cost label for Build. **KTLO** is the cost label for Run. v1 has Build and R&D only.

- **Day and month boundaries** follow `project-insights-v1` §5 requirement 4 and D14: the UI buckets in the viewer's zone, server-side readers in the acting account's zone. So the **agent profile's period spend** (today, this week, this month, last month) follows the viewer's zone, labelled with it. **Agent daily and monthly budgets reset at midnight and on the 1st in the zone of the earliest-created owner account** (agents have no zone, `away-digest-and-timezones-v1` Z1). Before TZ-1 ships, HQ's zone. **Agent budget bars** (profile, org page) and `cost show --self` always use this zone, not the viewer's, and are labelled with it, for example "Today (America/New_York)". On one profile, the period spend and the budget bars can therefore show different "today" figures when the two zones differ. Both are labelled, and the difference is expected.
- **Cost and tokens always show together**: a figure is "≈ $6.40 · 1.9 M tokens", never one alone.
- **Partial data** is marked, never zeroed: a runtime that reports no usage, or a resume whose first turn wasn't counted (F3), adds a note "Usage incomplete: {reason}" to every total it affects.

## 5. Requirements

### 5.1 Capture (v1)
1. Every usage report from every agent runtime the office runs (Claude Code and Codex in v1) becomes a usage record (§4). Copilot session runs are recorded from v1.1 (no adapter in v1.0). A session run with tokens but no price is attributed like any other, its cost shows "—", and its tokens count (C26).
2. Attribution order for each record, first match wins (C21, C25): (a) the task the agent is doing **work for** (reviewing it, or invoked for it as a helper); (b) the agent's current task at the time it was reported; (c) when the agent has no current task and exactly one In progress task or bug assigned to it (an In progress bug counts like an In progress task), that item (marked "by fallback"); (d) otherwise the project's or the org's Not on a task bucket (§4).
3. **A bug can be a current item**, like a task (today it can't, F17). Work on bugs is attributed to the bug.
4. Each record stores the price used. A later price change never changes a stored record.
5. Each record stores the attributed item's work type at that time (Build in v1).
6. Records are append-only. Corrections, including a move to another task, are new records that reference the one they correct (requirement 33, C28).
7. When the agent runs on a subscription plan, its records are marked API-equivalent. API-equivalent cost counts against dollar budgets (task and agent) and release caps like any other cost.

### 5.2 Work type (v1)
8. Every task and bug carries a work type. In v1 it is always Build, set at creation, and not editable (one choice). The task page and `tasks show` display "Build".
9. Every roll-up groups by work type, even in v1 where only R&D shows. A v2 Run type adds a group, not a migration.

### 5.3 Roll-ups (v1)
10. Roll-ups follow §4.1 exactly, from usage records, with no typed figures.
11. Cost follows the task's **current** plan: moving a task to another release or milestone moves its whole cost.
12. Every figure opens its records or items, and the list sums to the figure (the same rule as `project-insights-v1` AC-IN7-3).
13. The same query set serves the task page, Insights (from v1.1), the release header, the agent profile and the CLI, so totals match everywhere.

### 5.4 Budgets (v1)
14. **Task budget** (optional), in dollars or tokens. Set, changed or cleared by the owner or the project's manager only. **Only a person can lift a budget:** setting a first budget or lowering one may be done by the owner or the project manager, human or agent (`projects-planning-v1` §4.7). Raising, clearing and Allow once may be done only by a person: the owner, or a human project manager. An agent project manager is refused: "Only a person can raise, clear or extend a budget." This holds whether or not the budget is reached. A new value above the current limit is a Raise; one below it is lowering, accepted even at or below spent (requirement 18). A new value equal to the current limit is no change: it is accepted, and nothing happens. **Changing the unit** (dollars ↔ tokens) counts as clearing the budget and setting a new one, so only a person may do it: an agent project manager is refused with the same message. A person's unit change is accepted, and the new value is checked against spent, in the new unit, at once, like any set (requirement 18): at or below spent, the task stays stopped, or becomes stopped. **On a reached budget, a person's unit change is one change event** on the timeline (not a clear plus a set): the Inbox item stays if the new value is still at or below spent, and Allow once is re-armed, since it is a new value (requirement 22). **If the new value is above spent in the new unit, the change lifts the stop like a Raise:** the Inbox item clears and the task resumes as a Raise does (requirement 23). Covers every agent's cost on the task. A parent's budget covers its **total** (own records plus its subtasks'). A subtask may also have its own budget, which covers its own records (C22).
15. **(v1.1) Anyone may propose an estimate** when they create a task (*Emery's addition; the owner can cut it*): people and agents, Asked by included (`tasks new … --estimate-usd 5` or `--estimate-tokens 2000000`). It shows as "Estimate $5, proposed by Kai". It becomes the budget only when the owner or the project manager accepts it, or they set another. Accepting is setting: an agent project manager may accept it as a first budget or a lower one, not as a raise (requirement 14).
16. **Agent budget**, per day and per month, each optional, in dollars or tokens. Owner only. Each has its own unit: a daily dollar budget with a monthly token budget is allowed. The budget bars and `cost show --self` show each in its own unit.
17. **(v1.1) Release cap** (optional), in dollars or tokens (*Emery's addition; the owner can cut it*, CB-8). Set by the owner or the project manager only, because only they see amounts (requirement 26). Other release planners (`projects-planning-v1` §4.7) can't set it.
18. **At 80%** of any budget: one informational notice to whoever last set or changed it. Neutral styling, never amber, never an Inbox item. **Where notices go:** a person gets budget notices in the app; when the last setter is an agent (an agent project manager), it gets them as an org message in its agent inbox. This holds for every notice that goes to whoever last set or changed a budget (requirements 18, 19, 33). For a task budget, once per budget value: a new value (a raise or a change) re-arms it. For an agent budget, once per period (the day or the month): a new value re-arms it too.
    - **Checked on every set, change and cost record.** Setting or lowering a budget to at or below spent triggers the 100% stop at once, with no 80% notice. **On a budget already reached**, a new value at or below spent that isn't a Raise is accepted too: the task stays stopped (an agent stays paused), the Inbox item stays, and Allow once is re-armed against the new value, since it is a new value (requirement 22). Only a Raise or an Allow once whose result is still at or below spent is refused (requirement 22). Setting it between 80% and 100% sends the 80% notice at once. **Reopening is a check point:** a reopened task at or over its limit is stopped at once by its new status (`tasks-v1` AC-TK4-19).
19. **At 100% of a task budget:** every agent working on the task (reviewers and helpers included) finishes its current turn, then stops by the task's status:
    - **In progress:** the task moves to **Blocked, waiting on the owner, reason "Budget reached"** (a system move with no actor, `tasks-v1` §4.2, §12.2).
    - **To do or In review:** the task keeps its status and gets a **budget hold**. Agent turns on it (assignee, reviewer, helpers) are refused until the budget is resolved. The reviewer and the review are kept.
      - Starting a held To do task is refused: "T-12 is on budget hold: a person must raise it, allow 20% once or clear the budget." The refusal applies to To do only. Accepting a Hand-off on a held To do task isn't a start: the task stays To do and held.
      - **A person may finish a held task:** a human assignee or the owner may mark a held To do task **Done**. Reaching Done clears the hold and its Budget reached Inbox item (requirement 23). An agent's Done is refused: "T-12 is on budget hold: only a person can mark it Done."
      - **Approving** a held In review task to Done is allowed (a human reviewer or the owner), because finishing adds no cost. Reaching Done clears the hold and its Budget reached Inbox item (requirement 23). Agent turns stay refused: an agent reviewer's Approve is refused with "T-12 is on budget hold: only a person can approve it." **Cancel** and **reassign** are allowed too (reassigning doesn't lift the hold, requirement 23).
      - An **agent assignee can't withdraw** a held In review task: "T-12 is on budget hold: only a person can withdraw it from review." A **human assignee's withdraw** moves it to Blocked "Budget reached" at once, as request changes does (`tasks-v1` §4.2).
      - **Request changes** on a held In review task (by a human reviewer or the owner) is allowed. The task moves to In progress and, being over budget, at once to Blocked "Budget reached": the hold becomes a block, with the same Inbox item (§12.2).
    - **Both cases raise the same Inbox item:** every budget stop, block or hold, has exactly one Budget reached Inbox item for the owner (amber), whatever the task's status, a task Blocked on someone else or on the owner included. (A subtask stopped only by its parent's budget is covered by the parent's one item, below.) Actions: **Raise budget**, **Allow 20% more once**, **Stop** (Cancel on a task, Won't fix on a bug; actors under "Who may act").
    - **Who may act:** for a task budget, the owner and a human project manager may Raise, Allow once or clear it. An agent project manager is refused: "Only a person can raise, clear or extend a budget." (requirement 14). **Lowering** (a new value below the current limit) may be done by the owner or the project manager, human or agent, and is accepted even at or below spent: the task stays stopped and the Inbox item stays (requirement 18). A value above the current limit is a Raise, a person's action. For an agent budget, the owner only. **Stop** may be done by the owner or the project manager, human or agent: it spends nothing, and a stopped task or bug can be reopened. Stop records the reason "Budget reached: stopped by {actor}" by default, from the Inbox or the CLI; a reason given replaces it. On a task, Stop is Cancel; on a bug, Stop closes it as Won't fix, regardless of the usual bug close rights (§5.4 Bug statuses). The Inbox item goes to the owner. The project manager acts from the task page or the CLI.
    - **A Done task isn't stopped** when it reaches 100% (by a record move or a late turn). The overspend shows on its Cost section.
    - **A Cancelled task isn't stopped** either when it reaches 100%, like a Done task. Its cost records still count (§4.1).
    - **A top-level task already Blocked** (on someone else or on the owner) keeps its waiting-on and gets the hold, like a subtask, and the one Budget reached item. A task Blocked on the owner gets the hold and that one item, and also keeps its "Blocked on you" item: the two items have different causes. While held, it can't be unblocked into In progress (`tasks-v1` §4.2's Unblock row and §5: "T-12 is on budget hold: a person must raise it, allow 20% once or clear the budget."). When the budget resolves, the hold lifts and the Budget reached item clears; a task Blocked on someone else stays Blocked on them, and a task Blocked on the owner stays Blocked on the owner and keeps its "Blocked on you" item.
    - **A parent's budget** covers the parent and all its open subtasks. Each follows the rule above by its own status. A subtask moved to Blocked gets the reason "Parent budget reached". A subtask already Blocked on someone else keeps its waiting-on and also gets the hold. Subtasks stopped by their parent's budget have no Inbox item of their own: the parent's one item covers them, and they return with the parent. Request changes on a subtask held by its parent's budget moves it to Blocked "Parent budget reached", with no Inbox item of its own. A subtask that reaches its own budget stops only that subtask and gets its own Budget reached Inbox item. A subtask stopped by both its own budget and its parent's shows its own "Budget reached" (with its own Inbox item), and returns only when both are resolved.
    - **Notice:** whoever last set or changed the task budget (owner or project manager) gets a neutral notice at 100% too. Only the owner gets the Inbox item.
20. **At 100% of an agent's daily or monthly budget:** the agent pauses all work after its current turn and waits on the owner the same way. Its tasks keep their status: none is blocked or held, and the agent simply starts no turn. The pause is on the agent: Inbox item (amber), "Paused · Budget reached". Actions: **Raise budget**, **Allow 20% more once**, **Keep paused** (until the next day or month). Keep paused leaves the Inbox item open until the reset. A daily pause lifts **automatically** at the next day's start; a monthly one at the next month's start. When it lifts, the Inbox item clears and the owner gets a neutral notice ("Kai's daily budget reset. Kai is working again."), never amber (C27).
    - **Both limits reached:** an agent at 100% of both its daily and its monthly budget gets one Inbox item per period reached (two items), each resolved by its own actions. The pause lifts only when both are below their limits: a daily reset or a raise of the daily budget alone clears the daily item and leaves the agent paused on the monthly one.
21. **(v1.1, with requirement 17) A release cap only warns** in v1: neutral notices at 80% and 100% to whoever set it (the owner or the project manager, requirement 17), each once per cap value: a new value re-arms them. A cap's spent equals the release's cost (§4.1), deleted items included (C9). It never stops work and never makes an Inbox item.
22. "Allow 20% more once" ends the wait and raises the limit by 20% of the budget. **It is offered only at 100%:** on a budget not reached it is refused, "Allow 20% once is available only when the budget is reached." On a task budget, Raise and Allow once are a person's actions (requirement 14). For a task budget it works once per budget value: a new value (a raise or a change) re-arms it. For an agent's daily or monthly budget it works once per period (the day or the month), and applies to that period only. **Raise on an agent budget changes its standing daily or monthly value.** To allow more for the current period only, use Allow once. **Raise sets a new limit equal to the new value:** an earlier Allow once doesn't stack onto it. A new value re-arms Allow once, including mid-period for an agent budget. At the new limit the same stop applies, with only Raise and Stop (or Keep paused).
    - **A Raise must clear spent.** A Raise whose new limit is at or below spent is refused, naming the spent amount: "T-12 has spent $25.00: set a budget above that." **Allow once** is refused when 120% of the budget is still at or below spent: "Allowing 20% once still leaves T-12 at its budget ($25.00 spent): raise it instead." A refused Allow once doesn't use up the allowance. The task (or agent) stays stopped and the Inbox item stays. The same rule applies to an agent budget, against its spent for the current day or month ("Kai has spent $52.00 today: set a budget above that.", or "Kai has spent $52.00 this month: set a budget above that." for a monthly one; for Allow once, "Allowing 20% once still leaves Kai at today's budget ($25.00 spent): raise it instead.", or "this month's budget" for a monthly one). A second Allow once in the same period is refused: "Kai has already used today's 20% extension: raise the budget instead." ("this month's" for a monthly one), in the same form as a task's second use: "T-12 has already used its one 20% extension: raise the budget instead."
    - **A lower value is accepted.** On a reached budget, a new value at or below spent that isn't above the current limit (lowering it, by the owner or the project manager, human or agent, requirement 19) is accepted, not refused: the task (or agent) stays stopped, the Inbox item stays, and Allow once is re-armed against the new value, since it is a new value. Only a Raise or an Allow once whose result is still at or below spent is refused.
23. Raising the budget, allowing 20% more once, clearing the budget, or changing its unit to a value above spent in the new unit (each by a person allowed to: the owner, or a human project manager for a task budget; the owner for an agent budget; requirement 14) ends the wait, as does a person's cost move that drops spent below the current limit (requirement 33): five resume causes. An agent project manager's attempt is refused and ends nothing. So does the task reaching Done (a person marking a held To do task Done, or approving a held In review task). A Raise or Allow once that would leave the limit at or below spent is refused (requirement 22), so it never ends the wait. A lower value is accepted but ends nothing either (requirement 18). The Inbox item clears. A Blocked "Budget reached" task returns to In progress (a system move, §12.2), a held task's hold lifts, and an agent resumes. Subtasks follow their parent. Dismissing without acting is not offered.
    - **The hold or the block stays with the task** until the budget is resolved by one of the five causes above.
    - **Reassigning doesn't lift it.** Reassigning a task Blocked "Budget reached", or a subtask Blocked "Parent budget reached", moves it to To do and turns the block into a hold (`tasks-v1` §4.2): the wait, the Inbox item (the parent's, for a subtask) and Needs me stay. When the budget is resolved, the hold lifts and the task stays To do for the new assignee to pick up. Reassigning a held task keeps its hold. The new assignee's first turn is refused until then.
    - **Cancelling** the task clears the hold and the Inbox item. Its subtasks follow the cancel cascade (`tasks-v1` §4.2).
    - **Deleting** a task or bug clears its Budget reached block or hold and its Inbox item. Delete rights are unchanged: they follow `tasks-v1` and the existing `work.delete`, the owner only and in the app only, so an agent or a project manager can't delete to end a stop. Deleting a parent also clears those of its subtasks stopped by its budget or their own. A deleted item's cost still counts (C9): a deleted subtask's cost stays in its parent's subtasks figure, total and budget spent, so deleting a subtask never drops its parent below its limit by itself.
24. Every budget set, change, clear, 80% notice, 100% stop and override is recorded with actor and server time: on the task's timeline, on the release's history, and on the agent's history.
25. A budget whose agent's runtime reports no usage can't be enforced: setting it warns "{agent}'s runtime doesn't report usage, so this budget can't stop work." Setting a dollar budget on a task warns the same way when any run on it so far had no price, or the assignee's runtime has no price. A dollar budget on an agent whose runs have no price warns the same way, naming the gap ("…reports no price, so a dollar budget can't count its runs. Use a token budget.").

**Bug statuses.** A bug's budget follows requirement 19 by the bug's status, mapped as below. Status names are those in `project-insights-v1` §4.2 and `away-digest-and-timezones-v1` §4.3.

| Bug status | Stops as | Effect at 100% |
| --- | --- | --- |
| New, Triaged | To do | Budget hold |
| In progress (its first move there is "Started") | To do (hold, not block) | Budget hold: the bug stays In progress, agent turns on it are refused, and the owner gets the Budget reached Inbox item. Bugs have no Blocked status, so no block is used |
| Fixed, Closed · Verified | Done | Not stopped. Reaching Fixed clears a hold and its Inbox item, as Done does. On a held bug, only a person may set Fixed (below) |
| Closed as Duplicate, Won't fix or Can't reproduce | Cancelled | Not stopped; closing clears a hold and its Inbox item |

- **Moves on a held bug** (AC-CB6-16):
  - **New → Triaged** keeps the hold and is done by a person. Agent turns on a held bug are refused, so an agent can't triage it: "B-3 is on budget hold: only a person can triage it."
  - **A move to In progress** is refused, like starting a held To do task: "B-3 is on budget hold: a person must raise it, allow 20% once or clear the budget."
  - **Fixed** may be set only by a human assignee or the owner, mirroring a held task's Done (requirement 19). It clears the hold and its Budget reached Inbox item. An agent assignee is refused.
  - **In progress → Triaged** by a person keeps the hold.
- **Stop** on a bug's Budget reached item may be done by the owner or the project manager, human or agent (requirement 19): it spends nothing, and the bug can be reopened. It records the default reason "Budget reached: stopped by {actor}" unless a reason is given. It closes the bug as **Won't fix**, regardless of the usual bug close rights.
- **A reopened bug is a check point**, like a reopened task (requirement 18): at or over its limit, it is stopped at once by its new status.
- Bugs have no Blocked status (`project-insights-v1` §4.2), so a bug is never blocked by a budget: at every open status it gets a budget hold, cleared by the same causes as a task's hold (requirement 23). **[O]**

### 5.5 Who sees cost (v1)
26. The owner sees all cost. A project manager sees cost for their projects: on an agent's profile, only the records attributed to their projects, labelled "in your projects". An agent's daily and monthly budget bars are owner only, because they count spend from every project. Other members see none, except:
27. An agent sees, through the CLI, its own current task's budget, spent and remaining, and its own daily and monthly budget, spent and remaining (C29), in the budget's zone and labelled with it (§4). Nothing else, unless the agent is the project manager (requirement 26).
28. Any member sees a task's **budget state** (none, OK, 80%, reached) on tasks they can see, so they know why a task is blocked, without amounts. **[O]**
28a. **Repo files carry no amounts.** Files written to the project's repository (reports, retro files, evidence given to agents) never contain cost amounts or budget figures, because any member can read them. They may show tokens and "Budget reached", and point to the app, where requirement 26 decides who sees amounts (Eden's A109, Rev 15).

### 5.6 Price list, corrections, org page (v1)
29. **Price list.** The owner edits it in Settings › Costs: a rate per model, with an effective date. A custom rate (for example a negotiated discount) applies from its effective date forward. The effective date is today or later. Records already stored keep their price (requirement 4) (C24).
30. **Frozen "Spent at release."** When a release becomes Released, its total cost at that moment is stored and shown next to its current cost (C23). Re-releasing a reopened release replaces it with the new figure; the earlier value stays in the release's history (§4.1).
31. **(v1.1; `org-agent cost show --org` stays in v1.0) Org Cost page** (*Emery's addition; the owner can cut it*, CB-13), under Organization, owner only: totals for a period by project and by agent, R&D only, with the project Cost view's period filter and time-zone rules (C30).
32. **Attribution marks.** A record attributed by fallback (requirement 2c) is marked, so a wrong guess is easy to find and correct.
33. **Move a record.** The owner and the project manager can move a cost record to another task, or to "Not on a task", with a reason. A record moved to "Not on a task" goes to the source task's project bucket. The move is recorded in both tasks' history. A project manager can move a record only when both the source and the target (task, or project bucket) are in their projects. **A move that lowers the spent of a reached budget** is a person's action, like a Raise (requirement 14): the owner or a human project manager. That is any move of a record off the stopped task itself (one with a Budget reached block or a budget hold), off any of its subtasks (Done or Cancelled ones included, since their records count in the parent's total), or off a subtask whose parent's budget is reached. An agent project manager is refused: "Only a person can raise, clear or extend a budget." The original record stays; budgets and totals follow the corrected attribution (C28). A move re-checks both tasks. If the source drops below its current limit (an Allow once raises that limit), its Inbox item clears, its hold lifts (a Blocked "Budget reached" task returns to In progress), subtasks held or blocked by "Parent budget reached" return with it, and whoever last set or changed its budget and the owner get a neutral notice. If the target reaches 100%, it stops by the rule in requirement 19.

**Periods for `cost show` (v1.0, Rev 14).**
- **Default:** all time, from the first usage record to now.
- **Every ref accepts:**
  - `--period 7d|30d|90d`, rolling, as in `project-insights-v1`'s "v1.0 scope" Periods;
  - `--period release:R-n`;
  - a custom range, `--from YYYY-MM-DD --to YYYY-MM-DD`: whole days, inclusive.
- **An agent ref also accepts** `--period day|week|month`: the current calendar day, week (starting Monday) and month.
  - Day and month are the same periods the agent's daily and monthly budgets reset on (AC-CB5-1, AC-CB7-3).
  - These three use the budget's zone, and the output is labelled with it, as `--self` is ("Today (America/New_York) …").
- **Zone:** every other period, and every `--by period` bucket, uses the zone of the account the command acts for (§4.1, insights AC-IN7-5).
- **Applies to `--org` too.** There, `release:R-n` is refused with "A release belongs to a project: use cost show R-n".
- **Combining options:**
  - `--from` without `--to` runs to now.
  - `--to` without `--from` is a usage error.
  - `--period` together with `--from` or `--to` is a usage error.
- **`--by period` buckets:**
  - `7d`, `30d`, `90d` and `release:R-n` keep the Insights bucket sizes (by day for 7d; by week for 30d and 90d; a release by day when its span is 30 days or less, by week otherwise).
  - Every other period (all time, a custom range, and an agent's day, week or month) is bucketed by length:
    - 31 days or less: by day;
    - up to 26 weeks: by week;
    - longer: by month.

  A first or last bucket that covers part of a day, week or month is shown and marked "partial".

## 14. Leaning (v2, not final)

- **L1 (was Q10).** The work type follows where the item is planned. Items in the Build area (backlog, releases) are Build.
