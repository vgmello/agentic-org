## The request (the user, via ada, 2026-11-08)

> A **process** is a natural-language text file added to the organization. Agents look up their processes when they start, to understand what they have to do. Processes exist at the **organization** level, can be **overridden** at the **team** level, and a team can have its own. Levels: organization → team → **project** (the lowest). A lower level overrides a particular process from the level above, or adds its own. An agent can also have its own **private** processes. Processes are committed to the repo. This matters so we understand how the agents work.

The first real process is the branch → review → merge flow (ada's `branch-and-merge.md`), which carries the **one open branch per agent** rule. *(rev 4)* In the product it ships as two processes: `one-open-branch` (sealed) and `review-and-merge` (overridable), §4.

## 0. Decisions (proposed)

1. **A process is a doc kind** (`decisions-and-tech-debt-ux.md` §0.1): Markdown with front matter, written in plain words, read by agents and people alike. It's persistent knowledge, so it's a file in a repository, written through the tool and changed through the merge flow. Like every doc it has its own `id` (`doc-<ULID>`, decisions spec decision 2 and TPL-8). The files at each level are different docs, so an override can't share its parent's id. What they share is a separate stable key, **`process`** (for example `process: review-and-merge`), the same at every level, and that key is what matches a process across levels. The key is **unique per level and scope**: if two files at the same level and scope use the same key, neither applies, and the Processes view shows the clash until one is renamed (as DEC-7 does for a number used twice). *(rev 2)*
2. **Four levels, one effective set.** For a given agent and piece of work, the effective processes are: **organization** ⊕ the **team** that owns the work's project ⊕ the **project** ⊕ the agent's own **private** processes. Teams nest (`offices-and-teams-ux.md` §7.5), so the team level is a chain: the outermost parent team first, down to the project's own team, the nearer team winning. *(rev 2)* Processes are matched **by the `process` key** *(rev 2)*. With no current work (for example, an on-call or scheduled agent waking with no task), the set is the organization's processes plus its private ones; team and project processes join when it starts a task. *(rev 2)* The lowest level that defines a key wins (an **override**, which names the key and version it overrides: `overrides: review-and-merge@3`), and a new key adds a process (an **addition**).
3. **Sealed processes can't be overridden.** A process with `overridable: false` (sealed) applies as written at every lower level, and an override of it is refused with the reason. Only the owner seals at organization level. A team lead can seal a team process for its projects and for its sub-teams and their projects. *(rev 2)* *(rev 3)* On a project shared with another team, a seal doesn't silently lose: if a sibling team overrides or turns off the sealed key, that's a conflict (decision 6), the sealed version applies meanwhile ("Sealed by <team>; applies until the project decides"), and the project settles it with its own version, like any conflict (ada's design, decision 13).
4. **A lower level can turn an inherited process off**, if it's overridable, with a short file that says so and why (`status: off`, `reason`). The app shows "Turned off for <team or project name>: <reason>" (for example "Turned off for checkout: we report daily"). A sealed process can't be turned off.
5. **Private processes only add.** An agent's own processes are its personal working habits. They can't override or turn off anything inherited (otherwise the shared rules would mean nothing). *(rev 3)* A private file that sets `overrides:` or `status: off`, or uses an organization key, is refused when it's written (`invalid_request`, reason `private_only_adds`), with the case named: "Private processes only add: they can't override a process.", "…: they can't turn off a process." or "…: <key> is the organization's <name>. Use another name." One whose key is used at an inherited level (a team or the project, or the organization later) is caught when the set is computed (it depends on the project), isn't applied, and the agent's profile flags it: "Private processes only add: <name> isn't applied because it changes an inherited process." They live in the organization's handbook (`agents/<member id>/processes/`), so the organization owns them, the owner can read them and they stay as history after offboarding; the agent changes them through the merge flow and **the owner approves** (ada, A52).
6. **An agent in several teams follows the team of the work's project.** Its effective set depends on what it's working on: the team(s) of the current task's project. If the project is shared by two teams that both override a process, the agent follows the **organization's** version (or, if one team sealed it, the sealed version, decision 3 *(rev 3)*), and the conflict shows in Needs you for the project's leads and the owner until the project settles it with its own version, approved by any one of them (decision 8). Work isn't blocked. If the organization has no version of that process, neither override applies until the project resolves it (ada), unless one team sealed it (decision 3), in which case the sealed version applies meanwhile *(rev 3)*. If only one of the project's teams has a version (an override, an addition or turned off), there's no conflict and that version applies to the project. *(rev 2)*
7. **Agents read their processes when they start a task and when they wake** (the guidance moments **Starting a task** and **Waking up**, `decisions-and-tech-debt-ux.md` §6.2) *(rev 2)*: the names and one-line summaries of the effective set, plus **what changed since they last read it** (new versions), in full. `org-agent process list|show|why` gives the rest. *(rev 3)* What's delivered counts as read once the agent's runtime accepts the start or wake (the texts actually sent, not the ones past the 24 KiB limit of ada's design §3.4, which are named instead), or when the agent runs `process ack`.
8. **Changing a process goes through the merge flow:** a docs branch, a review, approval by the level's owner (organization: the owner, or a lead the owner flags **Can approve processes** for ordinary changes *(rev 4, U27)*: like Can approve hires, only the owner sets it, and organization-level changes that seal or unseal a process, turn off an enforced rule, or touch the autonomy processes or the critical list (§4a) stay with the owner (lower levels keep their own approvers, below); team: the team lead or the owner; project: a project lead, meaning the lead of any team the project belongs to (a shared project has one per team, `offices-and-teams-ux.md` §7.9), or the owner, who is the only approver when the project has no lead; private: the owner (A52)), then the merge. *(rev 2)* Each merged change bumps `version`, and agents see it the next time they start a task or wake. *(rev 2)* No one approves their own request, as for hires (`our-org-in-the-app.md` §7.1): a process change, or an **Allow once…** for one's own task, goes to another approver at that level (another lead of the project) or to the owner. The one exception is the owner, who approves their own changes, since nobody is above the owner (as for hires, APPR-3). On one's own change or task, **Approve** and **Allow once…** are disabled with "Another approver or the owner must approve this.", and `org-agent process approve` or `task allow-second-branch` refuses with `not_authorized` and the same text.
9. **Processes are the source of guidance and checklists.** A process can declare short prompts for guidance moments (`moments:`) and a checklist (`checklist:`). So "how we work" lives in one place, and the moments and checklists stay in step with it. A process's checklist and the project's default checklist (`work-items-ux.md` §9.1) both apply: a new task in scope gets the project's default checklist plus the steps of the project's processes (organization ⊕ team chain ⊕ project; private processes don't add steps, and assigning the task later doesn't change its checklist) *(rev 2)*, process steps after the project's, with duplicate steps (same text) merged and required winning. *(rev 2)* A process's prompt for a moment is shown after that moment's guidance text (`decisions-and-tech-debt-ux.md` §6.2), and only while the moment is **On**: turning a moment Off in Settings › Agent guidance hides both. It hides only those prompts: the effective set and the processes changed since the agent last read them are still delivered at start and wake (decision 7), because they're rules, not reminders. *(rev 2)*
10. **Retros change processes.** A retro action item of kind **Process** proposes a change to a process file (a diff), and lands through the merge flow like any process change; the owner's approval of the retro's items is the level approval (`retrospectives-ux.md` decision 6) *(rev 2)*.
11. **Leads and approvers who are agents are told in their inbox.** *(rev 2)* Wherever this spec puts an item in a lead's or approver's **Needs you** (a multi-team conflict, a refused start, a process change waiting for approval, a parent change that left an override drifting (§2), a docs branch open too long), that's for the owner and for people. A lead or approver who is an agent gets the same item in its inbox (woken if on call), as for hire approval (`our-org-in-the-app.md` §7.1), and acts with the CLI: `org-agent task allow-second-branch <task> --reason "…"`, or `org-agent process approve <doc id>` / `process reject <doc id> --reason "…"` for a process change, named by the changed file's doc id (`doc-<ULID>`) because the same key and version can be waiting at two levels; the inbox item gives the id, the level and scope, and the diff.

## 1. The process file

```markdown
---
id: doc-<ULID>                       # the doc id, like every doc (TPL-8)
process: review-and-merge            # stable key, the same at every level; matches overrides (rev 4: the one open branch rule is its own sealed process, one-open-branch)
name: Review and merge
kind: process
level: organization                  # organization | team | project | agent
scope: null                          # the team id, project key or agent id for lower levels
version: 3                           # bumped by each merged change
owner: ac-staff-engineer-ada
summary: Own review; the reviewer's READY; the lead's go; merge; clean up.
applies_to: every agent that changes a repository
overridable: true                    # false = sealed
status: active                       # draft | active | off (turned off at this level) | retired
overrides: null                      # for an override: the inherited process key and version, e.g. review-and-merge@3
moments:                             # optional short prompts (guidance moments, decisions-and-tech-debt §6.2)
  starting_task: "Plan small: one reviewable piece per branch."
  waking_up: "If your branch is waiting for review or the go, check on it first."
  finishing_task: "Ask the reviewer for READY on the exact commit."
checklist:                           # optional; added to the project's default checklist for tasks in scope
  - { text: "Own fresh review", required: true }
  - { text: "Reviewer's READY for the exact commit", required: true }
  - { text: "The lead's go", required: true }
---

# Branch, review and merge
(plain-language steps, like ada's example)
```

Each opens a branch for the level's approver, like any change.

## 4. The one open branch rule (the first process)

*(rev 4, U26)* Every new organization starts with two processes from ada's `branch-and-merge` file: **`one-open-branch`** (sealed: the rule the office enforces, so teams and projects can't override or turn it off; only the owner can unseal it at organization level) and **`review-and-merge`** (overridable: how changes get reviewed and merged, which teams may adapt). Real exceptions use **Allow once…**. Enforcement binds to `one-open-branch` (ada's design, A64). The product enforces it:

## 4a. Autonomy: Asks first and Full autonomy *(rev 4, the user)*

> The user (2026-11-09): "you do everything … depend on me only for critical things you can't resolve. Use your best judgment. If you don't know, spin up a new agent and bounce the idea with it until you reach consensus … sync up with me only if there's no consensus, or for critical decisions." And: "this should be part of a role definition or … a flag, full autonomous, which when that flag is on … would only call the user when consensus cannot be found or when it's a critical decision."

- **The autonomy level** is a setting on each agent, with two levels today: **Asks first** (the default) and **Full autonomy**. It's stored as a level, not a yes/no, so a later level (for example "Decides, reports daily") needs no change of shape.
- **Who sets it:** only the owner, in the agent's Settings and in Hire's Review, like Can approve hires. A role can carry a default (in its role file), shown in Hire's Review as "Full autonomy (the role's default)", and the owner confirms it there: a role never grants autonomy by itself, since the HR lead writes role files. A hire approved by an agent with Can approve hires (`our-org-in-the-app.md` §7.1) starts at Asks first; if its role suggests Full autonomy, the owner gets a Needs you item, "Cameron's role suggests Full autonomy. Give it?" with **Give Full autonomy** and **Keep Asks first**. No agent can set it, for itself or for agents it hires.
- **Where it shows:** a badge on the Agents roster and the quick view, "Full autonomy", a word plus an icon (never color alone); nothing for Asks first. Every change is an Activity row ("You gave ada Full autonomy"). Turning it on takes effect at the agent's next session; turning it off at its next start or wake, when processes are delivered (§3).
- **What it changes:** which of two sealed organization processes applies. Both ship with every new organization and only the owner can change them (decision 8):
  - **`asks-first`** (applies to agents at Asks first): before a non-routine call, ask your lead, or the owner at the top (a critical decision always goes to the owner, even when your lead is an agent), with the options and a recommendation, and keep working on everything else meanwhile.
  - **`decide-and-escalate`** (applies to agents at Full autonomy; ada's `docs/processes/decide-and-escalate.md`): decide routine and reversible calls yourself and write down what you decided and why; when unsure, consult a fresh peer, giving it the question and the facts, not your conclusion, until you agree; escalate only when there's no consensus (to your lead, or the owner at the top), when the decision is critical (always to the owner, even when your lead is an agent), or when only someone else can unblock you; keep working on everything else meanwhile.
- **A consult** is a subagent inside the agent's own run, so its cost counts toward that run (Insights) and its busy limit, with no separate run or hire. A runtime that can't start a subagent escalates instead of consulting.
- **Critical decisions** (Settings › Autonomy, the owner's): an editable list, by default **security, data loss, money or spend, irreversible or one-way, legal, product scope or priority**. Teams and projects can add items through their own processes; only the owner can remove one.
- **Autonomy changes when an agent asks, never what it may do.** Full autonomy doesn't let an agent approve hires (Can approve hires stays a separate flag, with Settings › Hiring's limits), approve its own changes, grant **Allow once…**, or pass a spending guardrail; spending stays on the critical list. Approvals other processes require (review READY, the lead's go, a process change's approval) still apply.
- **Escalations** reach the owner in **Needs you** (an agent lead, when it's the right person for a no-consensus question, gets it in its inbox, decision 11): "ada needs you: <question>", what it blocks, the options as buttons with the recommendation marked "Recommended", the peer's view ("The consult agreed" or "The consult disagreed: <why>") and **Reply…**. The answer goes back to the agent, like an Ask in Chat (`chat-ux.md` §2). States: waiting (with how long), answered ("Answered by you: <option>"), and withdrawn by the agent ("ada resolved it: <how>").
- **Decisions taken**, for auditing without noise: the main record is a **Decisions** section on the task (each: the decision, the options weighed, whether a peer was consulted and its view, and whether it can be undone). Each decision and consult is also one compact Activity row of kind **Decisions**, hidden from Home and from Activity's default view, shown with the Decisions filter. A decision with no current task goes on the agent's Activity. A lasting architectural decision becomes an ADR (`decisions-and-tech-debt-ux.md`), not a log entry.
- **For agents (CLI, proposed for ada, A73):** `org-agent decision record "<decision>" --option "…" --option "…" [--consulted "<the peer's view>"] [--reversible|--one-way] [--task <ref>]`, and `org-agent escalate "<question>" --option "…" --recommend "<option>" [--consulted "…"] [--blocks "<what>"]`.

## 5. UX acceptance criteria (PROC)

- PROC-1 · *(after v1.0, F2-12 R1)* *(rev 2)* A process is a Markdown file with front matter (id, process, name, level, scope, version, owner, summary, applies_to, overridable, status, overrides, and optional moments and checklist), created and changed through the tool and the merge flow. Its `id` is a doc id like every doc's (`doc-<ULID>`), and its `process` key is stable across levels; an override names the key and version it overrides (`review-and-merge@3`). The key is unique per level and scope: if two files at the same level and scope use the same key, neither applies, and the Processes view shows "Two processes use the key `<key>` in <scope>. Neither applies until one is renamed." with Rename… on both rows.
- PROC-2 · *(after v1.0, F2-12 R3)* *(rev 2)* An agent's effective set for a piece of work is organization ⊕ the work's team(s), each with its parent teams from the outermost down, ⊕ project ⊕ private, matched by the `process` key; the lowest level wins, new keys add. With no current work, it's organization ⊕ private.
- PROC-3 · *(after v1.0, F2-12 R3)* *(rev 4)* A sealed process can't be overridden or turned off, and the refusal says whose version isn't applied and why ("<Team>'s version of <process> isn't applied: the organization sealed it.
