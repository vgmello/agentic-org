Docs and PRDs: the answer

One living Overview per project, one PRD per feature, and releases that point at features.

Git is the source of truth

Docs stay Markdown in the project repo. Agents write them through git, on branches. The UI reads, renders and links back to the file and commit. The owner comments, approves or asks for changes in the UI. Comments on docs are new behaviour; where they are stored is engineering's call.

A Docs tab with one typed library

Overview, Feature PRDs (FEAT-n) with their status and progress, Decisions (ADR-n), Specs, Runbooks, Release notes, plus the designed EVAL, DEBT, LIM and EXC kinds.

Release notes

One per release (R-n), at docs/releases/R-n.md. Its doc id follows the design (tasks-projects-docs.md:782); Rowan decides.

Links both ways

A task shows its feature and PRD. A PRD shows its tasks, progress and releases. Approvals go to the Inbox, status changes to Activity, and search covers docs.

ProjectBuilding → Live → Archived
→
OverviewOne per project, living. What it is, who for, how it works now, current version. Kept in docs/brief.md.
Features · PRD eachFEAT-n. Proposed → Planned → In progress → Delivered → Retired. Links its tasks.
→
Release R-nLists the features it delivers and shows their PRDs. Delivered PRDs become the as-built record.
→
Release notesDrafted from done features and tasks at release time, approved by the owner, then frozen in docs/releases/R-n.md.

A change to a delivered feature is a new PRD ("Extends FEAT-7") or a revision with history, never a silent rewrite.

Why not one project PRD

It grows without bound and mixes shipped with planned, so nobody can tell what is true now.

Why not a PRD per version

A version is a slice of features. Per-version PRDs duplicate feature text and go stale the day after release.

Why one PRD per feature

It keeps its own history in git and answers "why does it work this way?" long after go-live.

Feature proposals

Grouped by when. One status vocabulary:

Exists
Built on origin/v1.
Designed
A spec or design on origin/v1 covers it; not built.
Partly designed
Part of the proposal is in a spec or design on origin/v1; the rest is new.
Decided
Settled in one of my PRDs, with stories and a release; not built.
New
In no spec, design or PRD yet.

Decisions I made (tell me if you disagree)

  1. ORelease notes are approved by the owner before they freeze. They reach the Inbox as an Approval, as proposed ADRs do.
  2. OLive is suggested, the owner confirms. The app suggests Live when the first release ships; nothing switches on its own.
  3. ON4 and L5 ship as one feature: one digest, scoped to the org or a team.
